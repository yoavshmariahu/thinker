System behaviors
The rules every change must keep

A behavior says what your system must always (or never) do, and where the code upholds it. An agent editing the code a behavior rests on is handed it first. They come from the design documents checked into the repository and are yours to edit or discard. A mutable behavior is revised when merged code changes it; a fixed one never is. Proposed behaviors are not requirements until you accept them.

Frequently asked questions
The same answers, with the rest of the documentation, at zerotime.dev/docs.

Where is my data stored? Does anything leave my machine?

The cache lives in the repository it describes, and it stays on your machine. Notes are under .thinker/local/, which git ignores; there is no team sharing or sync. Notes that an older version committed under .thinker/notes/ are still read. .thinker/config.json holds the configuration. Per machine, ~/.thinker/ holds the installed app, the usage log every serving is recorded in, and the ranking model. The Context report is read from the transcripts your agents already write; nothing is copied out of them.

Three things leave the machine, and nothing else:

  • Model calls go to the provider you already use for your agent. Learning and verification run through your agent's own login (claude, codex, gemini, cursor, or an Anthropic API key), or, in a desktop app (Claude Desktop, the Codex app, Cursor), through the app's own session. A session is distilled from a condensed transcript; verification sends a note with the diff of the code it rests on. Thinker runs no model and stores nothing of its own in the cloud.
  • Telemetry is counts only. An hourly report carries numbers: notes served, verdicts, token totals, the sums of the holdout comparison, with an install id and a hashed device id. It contains no code, note bodies, prompt text, file paths or repository URLs. THINKER_TELEMETRY=off or { "telemetry": false } in the config stops it.
  • The ranking model is downloaded once at install (about 23 MB) and runs on your machine. Ranking never calls a service.

This page listens on 127.0.0.1 only.

A repository with sensitive content can be turned off with thinker disable inside it. Thinker then does nothing there, in any clone or worktree: the hooks and the MCP server serve nothing, no session is distilled, and nothing is written into it. thinker enable turns it back on.

How does the cache work? What does it do to make my agents faster?

A note is a short rule, map or how-to about one part of the code, with file:Symbol pointers and a hash of the code it rests on. The cache is a set of such notes, and the work is in putting the right one in front of the agent without being asked:

  • On each request a hook picks the lexical candidates, then a local ranking model reads the request against them and serves up to two notes, only those it scores relevant. The agent starts at the code instead of searching for it.
  • On each file edit the rules resting on that file are served, so a trap on that code is in view while it is changed.
  • On demand, the MCP tool lookup answers one open question or fetches a note the hook listed; skill cards are among the notes.
  • Never stale. Every serving re-hashes the dependencies of every note against your working tree. A note whose code changed is held back, re-verified with the next batch (every three days), and served again once it is fresh.
  • Once per session. A note is served once, not for one-word turns, and not at all when nothing fits.

The cache keeps itself: each session is distilled once when it ends, stale notes that were served are re-verified every three days, notes the sessions never acted on are archived, and a note nobody was served in two weeks is deleted.

Where do the notes come from? Can I build the cache up front?

From your own sessions, and from nothing else. When a session ends, a model reads a condensed transcript of it (what was asked, read, run and changed) and saves what the session worked out that the next one would otherwise work out again, usually nothing or one note. The same call grades the notes the session was served: confirmed, contradicted (the note is corrected) or unused. A quiet session, with nothing served, no edit, no failure and little exploring, is skipped.

  • There is no build step. thinker setup connects your agents and nothing else; every git repository starts with an empty cache, and the hooks serve from it once it holds a few notes.
  • The spend is bounded. One model call per session, through your agent's login, and learning and maintenance together stop at a daily token cap (maintain.dailyTokens in .thinker/config.json).
  • You can add your own. thinker add takes a note you wrote, and telling your agent to remember something makes it a note when the session is distilled.
  • You can stop it. { "learn": { "sessions": false } } in the config stops learning from sessions in a repository; THINKER_NO_LEARN=1 stops all learning.

Can Thinker cut what my agents load into every session?

It shows you what to cut, and you decide. The Context view here and thinker context list every section of your instruction files, every skill and every tool with what it costs a session and how many sessions it bore on. A section you pick can be removed or compressed by a model: the diff is shown first, and Apply writes it to your working tree, uncommitted, for you to review and commit like any change. Nothing is cut on its own.

How can I tell if Thinker is helping my agents?

  • At the end of each turn one line says what was served and the code it pointed at. It does not say "saved": whether the agent acted on a note is known only once the session is assessed.
  • The Context view here, and thinker context, show where your agents' context goes: what each instruction section, skill and tool costs a session and how often sessions acted on it, so what you cut is measured on your own sessions.
  • thinker usage, and the usage under Cache here, show notes served, what the sessions did with them (confirmed, contradicted, unused), what learning and maintenance cost in tokens, and an estimate of the reads avoided.
  • The holdout is measured, not estimated. 15% of prompts are served nothing, chosen by a hash of the session and the turn, and what every turn cost is read from the session's transcript. Once twenty prompts stand on each side, the holdout section compares the cost per prompt: tool calls and tokens with notes against without, on your repository, by your agent.

A note served is not a note used. Read the confirmed and unused counts rather than the hit rate; a cache that serves often and is rarely acted on is costing tokens, and maintenance archives such notes over time.
