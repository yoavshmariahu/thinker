thinker documentation

Thinker is a persistent knowledge cache for coding agents. It keeps short, verified notes about your repository, serves the one that fits each request, learns from every session, and keeps itself correct as the code moves.

The Problem: When you start a prompt in a complex repository, coding agents spend 50–70% of their early turns running grep, reading package.json, tracing import trees, and hitting dead ends. This wastes minutes of wall time and burns tens of thousands of context tokens before any code is generated.

The Mental Model

Thinker is not a vector database or an ungrounded RAG system. It is a dependency-keyed knowledge cache stored locally under .thinker/ in your repository.

Each note is 3–12 lines answering a recurring question, with file:Symbol pointers into the code. Every pointer is tied to the exact definition it names by a content hash, so a note knows when the code under it changed.

1 Learn

Setup can build a cache from merged pull requests and one exploration session per source area. From then on every agent session is distilled into notes when it ends, and the pull requests your team merges are mined in the background.

2 Serve

Each request gets the note that fits it best, chosen by a small local model from the candidates that match it by words, through the agent's native hooks. The agent can ask for more through MCP tools, and the files it edits bring the notes resting on them.

3 Keep Correct

Every serving re-hashes every note's dependencies against your working tree. A note whose code changed is held back and re-verified with a fast model in the background; what the sessions acted on raises a note's confidence, what they contradicted corrects it. Nothing needs to be run by hand.

Install and Set Up

The install command from the landing page installs the tool under ~/.thinker and wires it into the agents on this machine, once, in their own settings. Run from inside a repository, it also sets that repository up. Anywhere else, run thinker setup inside a repository later. 

# Set a repository up: connect the agents, then ask whether to build the cache
thinker setup

# Build without asking: merged pull requests (--prs n, default 60) and one exploration session per source area (--areas n, default 12)
thinker setup --build

# Wire things up only; the cache grows from your sessions
thinker setup --no-build

Building runs through your agent's own login: about 5.5M tokens and twenty minutes with the defaults, most of them cached prompt reads. The estimate is printed in tokens and minutes before anything runs, and nothing is given in dollars, since most agents run on subscriptions.

Wiring is machine-wide, the cache is per repository. The hooks and the MCP server are present in every checkout and act only in one that thinker setup has set up. Elsewhere your agents are served nothing and learn nothing.

Which note is served is decided by a small local cross-encoder (23 MB) that reads your request together with each candidate note. The installer fetches it and thinker update keeps it; thinker ranker says whether it is in place. Without it, notes are ranked by words alone. Requirements: git, curl, tar, Node 20+, and at least one supported agent, logged in.

Claude Code

Hooks in ~/.claude/settings.json, the MCP server in ~/.claude.json:

  • Prompt hook: UserPromptSubmit adds the orientation notes to the prompt.
  • Edit hook: PostToolUse brings the notes resting on a file the agent edits.
  • Learning: Stop and SessionEnd distill the session once, in the background, and show a one-line summary of what was served.

Codex CLI

Hooks in ~/.codex/hooks.json and the MCP server in ~/.codex/config.toml, where the project and the hooks are also marked as trusted, so Codex asks nothing before running them or calling orient. The Codex desktop app reads the same file.

Gemini CLI

Prompt-time context, edit notes and the MCP server in ~/.gemini/settings.json. Gemini Code Assist's agent mode reads the same configuration.

Cursor

Hooks in ~/.cursor/hooks.json, the MCP server in ~/.cursor/mcp.json (approved by setup), and an always-applied rule in the checkout. Cursor's prompt hook cannot add context, so the notes are computed at prompt time and handed over with the first tool result; the rule also tells the agent to call orient.

Pi, Windsurf Cascade, Copilot CLI, OpenCode

Nothing machine-wide: thinker setup --clients pi,windsurf,copilot,opencode writes an extension (.pi/extensions/, .opencode/plugins/), hooks (.windsurf/hooks.json, .github/hooks/) or a rule into the checkout. Restart the host agent after setup. Each host's own trust and hook settings still apply, and where a host offers no channel for notes at prompt time, a rule asks the agent to call thinker itself.

How It Works

What a Note Is

A note answers a recurring question, not "what this file does". There are four kinds:

Kind What It Answers
map Where a recurring concern is handled, how control or data flows across files, the shape of a module area
howto How to build, test, run or lint, with the non-obvious flags
rule What a change must respect: an invariant, a convention, a trap, a fix not to undo, a reason
behavior A desired behavior of the system a person wrote down; the code must uphold it (see Desired Behaviors)

Each note stores its title, the questions it answers, a body with pointers, the files and symbols it rests on with their content hashes, its source (a session, a person, a pull request), its confidence and its status.

In a Session

  • Each request gets the note that fits it best, with the code behind its pointers inlined and a [6 call sites in 3 files] tag on each symbol it names. A note is served once per session, never while stale, and not at all for a one-word turn of conversation (status?). When nothing fits, nothing is served.
  • Each file the agent edits brings the notes resting on it, rules first, so a trap on that code is in front of the agent as it changes it.
  • MCP tools, for the agent's own questions: orient (up to five notes for a task, with the ones it did not serve listed by title), lookup (a question, or a note by id), find (the definitions whose name or body carry the words of a query, when no note answers it), drilldown (a definition whole, with one hop of callers and callees and the notes on it), review (a change against the notes, before a commit), remember (save a note) and feedback (correct one).
  • At the end of each turn one line says what was served: 🧠 thinker: 2 notes this turn (pointing at 2 files, ~7k tokens of code). It does not say "saved": whether the agent acted on a note is known only once the session is assessed.

Learning

  • Each session is distilled once, when it ends, through the agent's own login: up to three new notes, and a verdict on every note it was served. confirmed (the agent acted on it) raises confidence; contradicted (the trace shows a claim was wrong) corrects the body, keeps the history, and retires the note when its confidence falls below 0.3; unused lets it decay. A quiet session (nothing served, no edit, no failed command, little exploration) is skipped. Near-duplicates are merged.
  • Merged pull requests are mined into notes, fixes first, since the record of a fix is what a review draws on most. thinker mine-prs works through history; background maintenance keeps up with new ones. A repository whose work lands by direct commits can mine them instead (--git --fixes).
  • Agents and people write notes too: the remember tool, thinker add note.json, and thinker system add for a desired behavior.

Staying Correct

Traditional documentation goes stale the moment code changes. Thinker avoids this with fine-grained hashing and background upkeep:

  • A dependency is {path, symbol?}. With a symbol, Thinker hashes just that definition's block, so a note about AuthManager.verifyToken does not go stale because another method in the same file changed. thinker ast install adds tree-sitter grammars (Python, JavaScript, TypeScript, Go, Rust) for exact boundaries; otherwise a regex heuristic finds the block.
  • Every serving re-hashes the dependencies of every note against your working tree, uncommitted edits included.
  • A stale note is held back by the hooks, verified in the background and served once it is fresh again. orient and lookup called by the agent still return it, under a ⚠ STALE banner naming exactly what changed.
  • Verification sends the note, the diff of its changed dependencies and their current text to a small model (Haiku by default), which answers still_valid, update (body rewritten, history kept) or invalid (retired).
  • Maintenance runs by itself, from the prompt hooks at most every ten minutes and after a commit or merge: it re-verifies up to 10 stale notes (the recently served first), writes phrasings for new notes, distills up to 3 newly merged pull requests and archives what the sessions showed is not worth serving, under a cap of 2M tokens a day. What a run did is shown once at the end of the next turn.

Reviewing a Change

thinker review turns the cache around: instead of serving notes to an agent about to make a change, it checks a change against them. The MCP tool review is the same for an agent before it commits. 

thinker review                      # the working tree against HEAD
thinker review --staged             # what is about to be committed
thinker review --base origin/main   # the branch since its merge base
thinker review --ref <commit>       # one commit, read from git alone
thinker review --state src/auth/    # no change: the current code against the notes on it

A review is for two things: a change that undoes a fix the team already made, and a change that breaks a convention or a desired behavior the cache holds. Measured on real PostHog history, it caught every regression of a fix the cache held a note about, including the ones a plain reading of the diff missed. It is not for bugs in brand-new code, and it says so up front when most of the changed code carries no note.

It makes two model calls and merges what they find: one sees the diff and the code it touched, the other sees the notes resting on the changed code and the notes that bear on it. Every finding carries a file, a line, the evidence it rests on and the note it came from. The cache is treated as evidence, not truth: a note that already disagreed with the code before the change is reported as drift of the cache, never charged to the change, and nothing in the cache is rewritten by a review. --kinds behavior consults the desired behaviors alone, --dry makes no model call, --json gives the report as data and --strict exits 2 on an error, for CI.

Desired Behaviors

Every other kind of note is a claim about the code, and when they disagree the note yields. A behavior note is the other way round: a person writes down what the system must do and where that is upheld, and from then on a change must conform, or be called out for not conforming. 

thinker system                      # every behavior, and whether the code upholds it
thinker system add file.json --fixed
thinker system promote <id>         # a rule the cache already holds becomes a behavior
thinker system md                   # write them as .thinker/SYSTEM.md

A fixed behavior makes a change that stops upholding it an error, with the behavior quoted in full at the top of the review. A mutable one is a warning, and may be revised by a change that edits the note itself. Before a merge the behavior is the truth; once the change is merged, the behavior is revised to match the code, with the old text in its history. Agents can save one with remember (listed as proposed until thinker system accept) and read them all with lookup and kind: "behavior".

Sharing with Your Team

Sessions learn into .thinker/local/notes/, which ignores itself in git. The repository cache lives in .thinker/notes/ and travels through ordinary commits and pull requests. Both are served together; usage, staleness and corrections to shared notes stay local, so serving never changes a committed file. 

thinker share --dry       # the eligible notes, and why others are skipped
thinker share             # write them into .thinker/notes/
git add .thinker/notes/   # commit and open your normal pull request

A note must be fresh, rest on existing code and pass content checks; notes from a person, a document or a merged pull request are eligible, and a session's note needs one confirming assessment. Near-duplicates, home paths and secret-like strings are rejected. thinker list labels notes local or repo.

thinker setup installs git hooks: pre-commit checks the shared notes a commit touches against the staged code and repairs or removes what cannot be kept valid (originals go to .thinker/local/quarantine/), pre-push reports issues and always allows the push, and post-commit and post-merge run maintenance in the background. For CI, thinker share --check --base origin/main reports on the committed cache; --strict makes it fail.

Verifying in Your Repo

You don't need to take benchmark claims on faith. Thinker includes built-in commands to measure the impact directly on your repository: 

# 1. Benchmark agent efficiency on a recent merged PR:
thinker benchmark pr [number]

# 2. Or test a specific question with vs. without Thinker context:
thinker benchmark run "explain how permissions are validated on project exports"

# 3. View the latest side-by-side comparison report:
thinker benchmark report

How it works: Thinker makes two read-only agent calls, one without Thinker context and one with the relevant notes, and compares wall time, agent turns, tool calls, and token usage side by side. Both answers are saved under .thinker/benchmarks/ for human inspection. If the cache does not cover the question, no agent call is made and questions it does cover are offered instead.

Usage and the Holdout

thinker usage summarizes how the cache has been used on this machine: notes served and how, what the sessions did with them, what learning and maintenance cost in tokens, and an estimate of the reads avoided. --here limits it to this repository, --days 7 to a period, --json gives the data.

One number in it is measured rather than estimated. The hooks serve nothing in 15% of sessions, chosen by a hash of the session id so a session is held out for its whole length, and every session's cost is recorded from its own transcript: tool calls, model turns, input tokens. The Holdout section compares the sessions that got notes with the ones that had notes withheld, as medians per model, once five sessions stand on each side. This is what the notes do for your own work, on your own repository, by your own agent. holdout in the config changes the share or turns it off.

What Outcomes to Expect

Evaluated on real tasks from merged pull requests across frontier and fast coding models (Claude Fable via Claude Code, Gemini 3.8 Flash via Antigravity CLI, and GPT-6 Astra via Codex CLI), independently graded against calibrated acceptance criteria:

  • Tool & Exploration Efficiency (Consistent across all models): Reduces total tool calls by 17% to 22% and cuts file reads by 14% to 27%. Pre-seeded architecture notes prevent agents from burning early turns on repetitive grep and find loops.
  • Context & Token Savings (Consistent across all models): Cuts input context re-reads by 18% to 21% and output tokens by 11% to 22%.
  • Wall Clock Time (Consistent across all models): Completes tasks 7% to 14% faster (saving between 30 and 100+ seconds on complex tasks).
  • Correctness & Accuracy (Model-dependent): On frontier models (Claude Fable), pre-seeding conventions and invariants raised acceptance criteria accuracy by +10% and lifted complete task passes from 45% to 60% (+33% more tasks fully solved). Fast and reasoning models (Gemini Flash, GPT-6 Astra) maintained strict correctness parity (within single-run noise) while achieving significant token and tool reductions.

Note: The cache accelerates code navigation and eliminates redundant file exploration; it does not turn a weak model into a strong one. Run thinker benchmark report in your repository to measure your own baseline.

Configuration

Everything in .thinker/config.json is optional.

Key Effect
learn{"sessions": false} stops distilling sessions; pull requests and re-verification go on
maintainenabled, dailyTokens (2,000,000), verifyPerRun (10), phrasePerRun (8), prsPerRun (3)
archivekinds and unservedDays (30), or false
holdoutThe share of sessions served nothing (0.15; 0 or false: none)
ceThe cross-encoder: floor (0), maxNotes (1), or false to rank by words alone
snippets, noticefalse: no code behind the pointers; no end-of-turn line
distillModel, verifyModel, reviewModelThe model for each kind of call
telemetryfalse: no metrics sent

In the environment, THINKER_NO_LEARN=1 turns learning and maintenance off, THINKER_HOOKS=off silences the hooks, THINKER_MCP=off makes the MCP server offer no tools, and THINKER_LLM picks the agent that answers model calls (claude, codex, cursor, gemini, or anthropic with ANTHROPIC_API_KEY).

Privacy & Telemetry

Thinker collects pseudonymous daily effectiveness metrics (cache hit rate, total note count, estimated token savings) to monitor cache quality.

No code snippets, note bodies, prompt text, file paths, or repository URLs are ever collected or transmitted.

To opt out completely at any time: 

# In your shell environment:
export THINKER_TELEMETRY=off

# Or in .thinker/config.json:
{ "telemetry": false }
