A knowledge cache to help you catch regressions and boost coding agent efficiency

Thinker’s model-agnostic knowledge cache works across coding models and agents. It uses frontier models to build and maintain knowledge from code, sessions, and merged pull requests, and a small local ranking model to choose which notes to serve. Dependency-based invalidation and verification keep the cache fresh, helping agents catch regressions and complete tasks with fewer tokens.

Hooks hand the agent the note that fits each request.

3

Keep current

Sessions and merged pull requests become notes. A note whose code changed is held back and re-verified. Nothing is run by hand.

Everything lives under .thinker/ in the repository. Notes are keyed to the exact definitions they describe by content hash, so the cache knows when the code under a note has moved and never serves a claim it cannot stand behind.

Install and set up

The install command from the landing page installs the tool under ~/.thinker and wires it into the agents on this machine, once, in their own settings, asking nothing in the terminal. It ends by opening the warm-up page in your browser: the repositories your agents worked in over the last 30 days, each with a build estimate. Pick the ones to build a cache for now; every other git repository gets an empty cache with its first session and grows from there. 

# Open the warm-up page again any time
thinker ui --tab warmup

# Build one repository's cache from the terminal instead: mine merged PRs (--prs n, default 60);
# a build reads pull requests only; it does not explore the code
thinker setup --build

Working in a large repository? Setup offers Full repo or Specify project directories. Enter a project name and comma-separated directories such as apps/web, packages/ui. Thinker saves thinker.project.json and estimates the build for your selection. The installer offers the same choice. 

# Or save a project before onboarding
thinker project init apps/web packages/ui --name "Web app"
thinker setup --build --yes

setup and mine-prs reuse the saved project. Use --project other.project.json for another selection or --full-repo for one full-repository run. Paths are relative to the repository root. History mining focuses on the selected directories; retrieval, review, and ongoing learning still use the whole repository cache.

Building runs through your agent's own login: roughly 700k to 900k tokens and about ten minutes with the defaults (60 merged pull requests). The estimate is printed in tokens and minutes before anything runs, never in dollars, since most agents run on subscriptions.

The wiring is machine-wide, the cache is per repository. Hooks and the MCP server are present in every git checkout, and each checkout keeps its own cache under .thinker/, started on first use and excluded from git status through .git/info/exclude. Outside a git repository your agents are served nothing and learn nothing.

Requirements: git, curl, tar, Node 20+, and at least one supported agent, logged in. thinker ranker shows the configured ranking mode.

The knowledge cache

What a note is

A note answers a recurring question about the repository, not "what this file does". It is 3 to 12 lines with file:Symbol pointers into the code, and it comes in four kinds:

KindWhat it answers
ruleWhat a change must respect: an invariant, a convention, a trap, a fix not to undo and why. The kind a review draws on most.
mapWhere a recurring concern is handled, how control or data flows across files, the shape of a module area
howtoHow to build, test, run or lint, with the non-obvious flags
behaviorA desired behavior of the system a person wrote down; the code must uphold it (see Desired behaviors)

Each note stores its title, the questions it answers, its body, the files and symbols it rests on with their content hashes, its source (a session, a pull request, a person), its confidence and its status. A note's pointers are its dependencies: a note about AuthManager.verifyToken hashes that definition alone, so it does not go stale because another method in the same file changed.

Building the cache

thinker setup --build fills the cache from merged pull requests, and prints what it will cost in tokens and minutes before spending anything. Ctrl-C stops it at any time and keeps every note saved so far; the cache keeps growing from your sessions and a few merged pull requests per background run.

  • Merged pull requests, fixes first. Up to 60 of them are distilled into rules: what the symptom was, what the fix changed, and what a later change must not undo. The record of a fix is what a reviewing agent draws on most. Every pull request looked at is recorded in .thinker/prs.json, so none is distilled twice.
thinker setup --build --prs 100              # more history
thinker mine-prs                             # later: go further back through merged pull requests, 20 at a time
thinker mine-prs --git --fixes               # no GitHub: fix commits from git history

A build starts by reading the design documents checked into the repository (READMEs beside the code, design files) and saves the rules they state as desired behaviors (thinker system docs runs that step alone); it ends by drafting more candidates from the strongest rule notes for a person to accept or discard (thinker system propose). Without a build, the cache starts empty and grows from your sessions.

Keeping it current

A cache that drifts from the code is worse than none. Thinker keeps itself correct in three ways, all in the background, under a cap of 2M tokens a day:

It learns from every session

  • Each session is distilled once, when it ends, through the agent's own login: up to three new notes, and a verdict on every note it was served. confirmed (the agent acted on it) raises confidence; contradicted (the trace shows a claim was wrong) corrects the body and keeps the history; unused lets it decay. Near-duplicates are merged. A quiet session with nothing to learn from is skipped.
  • Newly merged pull requests are mined as they land, fixes first, so the next review already knows about the last fix.
  • Agents and people add notes too: the remember tool, thinker add, and thinker system add for a desired behavior.

It knows when a note is stale

  • Every serving re-hashes the dependencies of every note against your working tree, uncommitted edits included. A note whose code changed is marked stale and names exactly what changed.
  • A stale note is never served by the hooks. It is held back, re-verified in the background, and served again once it is fresh. orient and lookup called by the agent still return it, under a ⚠ STALE banner.
  • Verification sends the note, the diff of its changed dependencies and their current text to a small model, which answers still_valid, update (body rewritten, history kept) or invalid (retired).
  • The block is found by a tree-sitter parser for Python, JavaScript, TypeScript, Go and Rust, which comes with the install. Other languages, and code the parser cannot read, use a regex heuristic.

It maintains itself

Maintenance runs from the prompt hooks and after every commit or merge, at most once every four hours: it re-verifies up to 10 stale notes (the recently served first), mines up to 3 newly merged pull requests, writes retrieval phrasings for new notes, and archives notes the sessions showed are not worth serving. What a run did is shown once at the end of the next turn. thinker maintain --dry previews the next run; thinker verify re-checks stale notes now.

Local by default. Learned notes live in .thinker/local/, which git ignores. thinker export and thinker import back a cache up and restore it, checked against the checkout it lands in.
Code Review

Desired behaviors

Every other kind of note is a claim about the code, and when they disagree the note yields. A behavior note is the other way round: a person writes down what the system must do and where that is upheld, and from then on a change must conform, or be called out for not conforming. 

thinker system                      # every behavior, and whether the code upholds it
thinker system docs                 # the rules the checked-in READMEs and design documents state
thinker system add file.json --fixed
thinker system promote <id>         # a rule the cache already holds becomes a behavior
thinker system propose              # drafts from the build, and rules worth promoting
thinker system md                   # write them as .thinker/SYSTEM.md
thinker ui                          # accept, edit or discard them in the browser

A fixed behavior is never revised by a change; a mutable one is revised when merged code changes it. Either way the agent reviewing a change that touches the code a behavior governs is handed that behavior.

Efficient coding

In a session

Nothing changes in how you work. The hooks put the right note in front of the agent at the right moment, and the agent starts at the code it needs instead of searching for it.

  • Each request gets the note that fits it, with file:Symbol pointers into the code and a [6 call sites in 3 files] tag on each symbol it names. A local ranking model reads the request with the best lexical candidates and serves one note, only when it scores it relevant; when it is missing, notes are ranked by words alone. A note is served once per session, never while stale, and not at all for a one-word turn of conversation. When nothing fits, nothing is served.
  • Each file the agent edits brings the notes resting on it, rules first, so a trap on that code is in front of the agent as it changes it.
  • At the end of each turn one line says what was served: 🧠 thinker: 2 notes this turn (pointing at 2 files, ~7k tokens of code). It does not say "saved": whether the agent acted on a note is known only once the session is assessed.

Measured on real tasks with and without thinker, every model tested used 18% fewer input tokens per task and finished 10% sooner. .

Tools the agent can call

Beyond what the hooks serve, the MCP server gives the agent the cache and the code graph on demand:

ToolWhat it does
orientUp to five notes for a task, with the code behind the main pointers, and the notes it did not serve listed by title
lookupOne specific question, or a note by id; kind: "behavior" for the desired behaviors
findThe definitions whose name or body carry the words of a query, as pointers with their lines, when no note answers it
drilldownA definition whole, with one hop of callers and callees and the notes resting on it
remember, feedbackSave a note the agent worked out; confirm or correct one it was served

The same tools exist on the command line (thinker orient "<task>", lookup, find, drilldown). The first prompt of a session tells the agent that find and drilldown exist and how to load them.

Measure it yourself

Benchmark in your repo

You do not need to take the benchmarks on faith. Thinker can run the same paired comparison on your own repository: 

# A recent merged pull request, with and without the cache
thinker benchmark pr [number]

# A question the cache covers (Enter takes the first), or your own
thinker benchmark run "how are permissions checked on project exports"

# The latest comparison again
thinker benchmark report

It makes two read-only agent calls, one without thinker and one with the relevant notes, and compares wall time, turns, tool calls and tokens side by side. Both answers are saved under .thinker/benchmarks/ so you can judge their quality yourself; speed alone is not a correctness score. If the cache does not cover a question, no agent call is made and questions it does cover are offered instead.

Usage and the holdout

thinker usage summarizes how the cache has been used on this machine: notes served and how, what the sessions did with them, what learning and maintenance cost in tokens, and an estimate of the reads avoided. --here limits it to this repository, --days 7 to a period, --json gives the data. The same numbers, with the notes your agents saw most, are in the Usage view of thinker ui.

One number in it is measured rather than estimated. The hooks serve nothing in 15% of sessions, chosen by a hash of the session id so a session is held out for its whole length, and every session's cost is recorded from its own transcript. The holdout section compares the sessions that got notes with the ones that had notes withheld, as medians per model, once five sessions stand on each side. This is what the notes do for your own work, on your own repository, by your own agent. holdout in the config changes the share or turns it off.

thinker ui --port 4800 --no-open    # a fixed port, without opening a browser

Configuration

Everything in .thinker/config.json is optional.

KeyEffect
learn{"sessions": false} stops distilling sessions; pull requests and re-verification go on
maintainenabled, dailyTokens (2,000,000), verifyPerRun (10), phrasePerRun (8), prsPerRun (3), docs (true), docsPerRun (3: new or changed design documents read into behaviors per run)
archivekinds and unservedDays (30), or false

In the environment, THINKER_NO_LEARN=1 turns learning and maintenance off, THINKER_HOOKS=off silences the hooks, THINKER_MCP=off makes the MCP server offer no tools, and THINKER_LLM picks the agent that answers model calls (claude, codex, cursor, gemini, or anthropic with ANTHROPIC_API_KEY).

Privacy and telemetry

Thinker sends pseudonymous daily effectiveness metrics (cache hit rate, note count, estimated token savings, and the totals of the holdout comparison: session counts and summed tool calls and tokens of sessions with and without notes) to monitor cache quality. These telemetry reports contain no code, note bodies, prompt text, file paths or repository URLs. Note ranking runs on your machine. Learning and verification use your configured model provider. The telemetry opt-out below does not disable those model calls. 

# Opt out in your shell environment:
export THINKER_TELEMETRY=off

# Or in .thinker/config.json:
{ "telemetry": false }
FAQ

Frequently asked questions

Where is my data stored? Does anything leave my machine?

The cache lives in the repository it describes. Notes built from pull requests and notes shared with the team are under .thinker/notes/, committed and reviewed like code. What the sessions on this checkout learned is under .thinker/local/, which git ignores. .thinker/config.json holds the configuration and .thinker/prs.json the list of pull requests already read. Per machine, ~/.thinker/ holds the installed app, the usage log every serving is recorded in, and the ranking model.

Three things leave the machine, and nothing else:

  • Model calls go to the provider you already use for your agent. Learning, verification and mining run through your agent's own login (claude, codex, gemini, cursor, or an Anthropic API key). A session is distilled from a condensed transcript; a pull request is read as its title, description, review comments and diff; verification sends a note with the diff of the code it rests on. Thinker runs no model and stores nothing of its own in the cloud.
  • Telemetry is counts only. An hourly report carries numbers: notes served, verdicts, token totals, the sums of the holdout comparison, with an install id and a hashed device id. It contains no code, note bodies, prompt text, file paths or repository URLs. THINKER_TELEMETRY=off or { "telemetry": false } in the config stops it; see Privacy and telemetry.
  • The ranking model is downloaded once at install (about 23 MB) and runs on your machine. Ranking never calls a service.

gh reads merged pull requests from GitHub during mining; it posts nothing. The local page of thinker ui listens on 127.0.0.1 only. Notes reach teammates through git alone.

A repository with sensitive content can be turned off on the warm-up page of thinker ui, or with thinker disable inside it. Thinker then does nothing there, in any clone or worktree: the hooks and the MCP server serve nothing, no session is distilled, no pull request is read, and nothing is written into it. thinker enable turns it back on.

How does the cache work? What does it do to make my agents faster?

A note is a short rule, map or how-to about one part of the code, with file:Symbol pointers and a hash of the code it rests on. The cache is a set of such notes, and the work is in putting the right one in front of the agent without being asked:

  • On each request a hook picks the lexical candidates, then a local ranking model reads the request against them and serves one note only when it scores it relevant, with the code behind its pointers and a count of call sites for each symbol named. The agent starts at the code instead of searching for it.
  • On each file edit the notes resting on that file are served, rules first, so a trap on that code is in view while it is changed.
  • On demand, the MCP tools orient, lookup, find and drilldown give the agent notes and the code graph when the hooks served nothing.
  • Never stale. Every serving re-hashes the dependencies of every note against your working tree. A note whose code changed is held back, re-verified in the background, and served again once it is fresh.
  • Once per session. A note is served once, not for one-word turns, and not at all when nothing fits.
  • Reviews draw on the same notes. The record of a past fix is what lets an agent reviewing a change say that it undoes one.

The cache keeps itself: each session is distilled once when it ends, newly merged pull requests are mined as they land, and a maintenance run every four hours re-verifies stale notes and archives the ones sessions never acted on. See Keeping it current.

Why does mining take so long? Can I skip it?

Each merged pull request is read by a frontier model through your agent's login: title, description, review comments and the diff, about 14k tokens and 8 seconds per pull request, four at a time. The default build reads up to 60 of them, then reads the design documents, writes search phrasings for every new note, and drafts desired behaviors from the strongest rules, each a model call. Rate limits on the login stretch it further. The estimate in tokens and minutes is printed before anything is spent.

Yes, you can skip it, and nothing stops working:

  • Answer no at setup, or run thinker setup --no-build. Thinker is wired and the cache grows from your own sessions.
  • Pick Shallow: the newest 30% of the same pull requests.
  • Ctrl-C at any point keeps every note saved so far. thinker mine-prs continues where it stopped, 20 pull requests at a time, and the background maintenance mines a few new ones per run anyway.

What a build gives you that sessions cannot is the record of past fixes, which is what a reviewing agent draws on most. A repository with little history loses little by skipping it.

How can I tell if Thinker is helping my agents?

  • At the end of each turn one line says what was served and the code it pointed at. It does not say "saved": whether the agent acted on a note is known only once the session is assessed.
  • thinker usage, and the Usage view of thinker ui, show notes served, what the sessions did with them (confirmed, contradicted, unused), what learning and maintenance cost in tokens, and an estimate of the reads avoided.
  • The holdout is measured, not estimated. 15% of sessions are served nothing, chosen by session id, and every session's cost is read from its own transcript. Once five sessions stand on each side, the holdout section compares them as medians per model: tool calls and tokens with notes against without, on your repository, by your agent.
  • thinker benchmark pr runs a recent merged pull request with and without the cache and compares time, turns, tool calls and tokens; both answers are saved under .thinker/benchmarks/ so you can judge their quality. See Benchmark in your repo.

A note served is not a note used. Read the confirmed and unused counts rather than the hit rate; a cache that serves often and is rarely acted on is costing tokens, and maintenance archives such notes over time.
