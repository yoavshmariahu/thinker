Think ahead. Save context.

Every model call your coding agent makes re-reads the same things: the instruction file, the skill list, every MCP server's tool definitions, every tool result so far. Most of it is never acted on. Thinker shows you where the context goes, part by part, and lets you cut the parts your sessions do not use.

  • See it. The Context page reads your agents' own session transcripts and shows input tokens a session split into instruction files, skills, MCP servers, plugins, built-in tools and tool outputs, for one repository or all of them. Each section, skill and tool stands beside what it costs and how often sessions acted on it, with the waste flagged.
  • Cut it. Compress or remove instruction sections as a diff you apply; keep only the sections that matter in a trimmed copy for this checkout; switch unused skills and tools off from the next session, with a backup; compress long tool outputs before the agent reads them. Every cut is shown first and undone with one command.
  • Remember instead. The knowledge cache: what your agent works out in a session becomes a short note pinned to the code it describes, served on the requests it fits and re-checked when that code changes, so the agent reads less to find its way.

How it fits together

1

See

Thinker reads your agents' own session transcripts and shows where the context goes: what each instruction section, skill, tool and tool output costs a session, and how often sessions act on it.

2

Cut

Compress or remove the sections no session uses, keep a trimmed copy for this checkout, switch unused skills and tools off, compress long tool results. Each cut is shown first and undone with one command.

3

Remember

What a session works out becomes a short note pinned to the code it describes, served on the requests it fits and re-verified when that code changes, so the agent reads less to find its way.

Everything lives on your machine: the report is read from the transcripts the agents already write, and the notes sit under .thinker/ in the repository, keyed to the exact definitions they describe by content hash, so the cache knows when the code under a note has moved and never serves a claim it cannot stand behind.

Where the context goes

The Context page

thinker ui opens on it; thinker context prints the same report in the terminal (--days 7, --json). Everything is read from the agents' own session transcripts on this machine. Nothing is sent anywhere, and the report changes nothing by itself: every cut is a choice you make, shown first, undone with one command.

Why a few thousand tokens matter

An agent's context is sent whole on every model call. The instruction file, the skill list, every MCP server's tool definitions and every tool result so far are re-read each time, and a coding session makes tens of calls. So a part's cost is its size times the calls: a 4k-token section read by 40 calls is 160k input tokens, and a 7k-token file read on the third call is paid on every call after it.

Two things follow. A token cut from the fixed part is cut from every call, so a 1,200-token section nobody acts on costs far more than its size suggests. And a tool result is cheap once and expensive as it stays: compressing it saves on every call that follows, not only the one that read it.

What it shows

Input tokens over time, as stacked columns by day or week, total or per session, split into the parts the agent reads on every model call. The page sorts by the cost a session: tokens times model calls.

One part at a time, as cards. Each instruction section, skill and tool stands beside three measures:

What you can cut

Four cuts, one for each kind of context. Each shows what it will do before it does it, is a command too, and has one undo. The mechanism is given for each, so you know exactly what changes on disk.

Compress or remove an instruction section

Pick the sections no session acts on. Compress has a model rewrite them to about a third of the length; it is told to keep every rule, command, flag, config key, default and path, and to drop history, measurements, rationale and repetition. Remove drops the section; a heading with subsections keeps its heading line.

How
The diff is shown first. Apply writes exactly that text to AGENTS.md (or CLAUDE.md) in your working tree, uncommitted, and refuses when the file changed since the preview. No commit and no pull request: review it with git diff, then commit it or drop it.
Command
thinker instructions --compress <ids> [--apply], or --remove <ids>
Undo
git checkout the file.
Agents
Every agent that reads the file.

Keep a trimmed copy for this checkout

When the team's file must stay as it is, keep only the sections that matter here and let the agents in this checkout read those. It is a selection of the team's own text, never a rewrite of it.

How
The kept sections are written verbatim to AGENTS.override.md, which Codex reads in place of AGENTS.md, and to CLAUDE.local.md for Claude Code; a CLAUDE.md that is a copy of or a link to AGENTS.md is skipped through claudeMdExcludes in .claude/settings.local.json, and one with text of its own is left alone. Both copies are kept out of git through .git/info/exclude and rewritten whenever AGENTS.md changes.
Command
thinker instructions --core "Title, Title" (--cursor also for Cursor)
Undo
Remove the trimmed copy, or thinker instructions --off: the copies are deleted and the team's file is read again.
Agents
Codex and Claude Code; Cursor on request. The others have no local replacement that leaves the team's files alone.

Switch skills, MCP servers, plugins and built-in tools off

A skill's description, an MCP server's tool definitions and a plugin's are loaded into every session whether or not anything uses them. Switch off takes one out of the next session's context for this repository. A skill switched off still runs when you type /name. Claude Code's own tool definitions go the same way, from the Built-in tools cards; the file, shell and search tools are never offered.

How
The setting in the agent's own files that hides the source, written for this repository alone. Claude Code: skillOverrides (user-invocable-only), enabledPlugins, disabledMcpjsonServers and, for a built-in tool, permissions.deny in .claude/settings.local.json; or disabledMcpServers in this repository's entry of ~/.claude.json, what /mcp disable writes. Codex: enabled = false in the checkout's .codex/config.toml, a skill by its path in ~/.codex/config.toml. Cursor: the server's entry in ~/.cursor/mcp.json, for every repository. Every file is backed up first under ~/.thinker/state/harness-backups/.
Command
thinker harness --off "<label>"; thinker context --switch-off <labels> --builtin for a built-in tool
Undo
Turn back on, or thinker harness --undo [names]: each file is put back as it was.
Agents
Claude Code and Codex; Cursor for MCP servers.

Compress tool outputs

A tool result stays in the conversation, so every model call after it reads it again: a whole-file read is paid for twenty times over. Compression keeps what the agent was looking for and names what it left out, so the agent can ask for any range.

How
Claude Code's tool hook may replace a result before the model reads it; nothing thinker serves ever leaves the context again, so this is the one place tokens are taken out instead of added. Three shapes are trimmed. A whole-file read becomes the lines around the session's recent search patterns and the request's identifiers, every omitted range named with the definitions it holds and a last line saying how to read it. A test run becomes its counts and each distinct failure once, the full log kept under .thinker/state/tests/. A large search becomes its hits grouped per file. Any other output past the level's cap is cut to it. Moderate keeps 40 lines each side of a hit and caps at about 3k tokens; High keeps 15 and caps at about 1k. A file under 120 lines, one with no hit, or one where the kept lines reach 60% of it passes whole.
Command
thinker context --output-compression <tools> --level high|moderate|off, per tool: Read, Bash, or a shell program by name (Bash:sed)
Undo
The same with --level off, or No compression on the page. It is a setting in .thinker/config.json; nothing already in a conversation changes.
Agents
Claude Code only.

Correctness and undo

Every cut removes something the agent might have read. What keeps that from costing you a task:

  • Nothing is cut by itself. The report measures. Each cut is your choice, shown first as a diff, a setting or a sample result, and every one is reversible with one command.
  • Use is measured before you cut. A section applied in 90% of sessions is never flagged, whatever it costs. Start with high waste: large, and used in almost no session. The saving shown is the most a cut can save; a session that needed the part goes without it.
  • Compression keeps the rules. The model that shortens a section is told to keep every instruction, command, flag, default and path and to drop history, numbers and rationale, and you read the diff before Apply. Remove is yours to judge; in doubt, compress.
  • A trimmed result says what it left out. A compressed file read names each omitted range and how to read it back, so the cost of a wrong guess is a second read, not a missed fact. A file the trim would not shorten passes whole, and full test logs stay on disk.
  • Everything undoes with one command. git checkout for an edited section, thinker instructions --off for the trimmed copy, thinker harness --undo for anything switched off, --level off for compression. The FAQ lists what each cut writes.

What the numbers are. Tokens are counted from the transcripts at about four characters a token, times the model calls the transcript records. A tool output's cost is its tokens times the calls left after it; a compaction, which drops old results, is not seen, so that part is an upper estimate. The waste flags are measurements of use, not a promise: whether the agent then misses a cut section is what followed and missed are there to show, on your own sessions. No benchmark is claimed for the cuts; the benchmarks are about the cache.

Install and set up

The install command from the landing page installs the tool under ~/.thinker and wires it into the agents on this machine, once, in their own settings, asking nothing in the terminal. Then it reads the agents' own transcripts of the last 30 days in the five repositories they worked in most and prints where their context goes and what to cut first: the sections of AGENTS.md, the skills and the tools that cost the most in the sessions that did not use them, with the saving each is worth at most (thinker context --machine prints the same report any time). On a machine with a display it then opens the local page on that report over every repository, where the suggestions are reviewed and applied. From then on every git repository gets a cache that grows from your sessions; nothing is built. 

# Open the local page again any time
thinker ui
thinker ui --tab context --all      # the Context view over every repository, as the installer opens it

# No browser, or a script: set one repository up from the terminal
thinker setup                       # connects the agents and prints the repository's own report; --no-ui keeps the page closed
The wiring is machine-wide, the cache is per repository. Hooks and the MCP server are present in every git checkout, and each checkout keeps its own cache under .thinker/, started on first use and excluded from git status through .git/info/exclude. Outside a git repository your agents are served nothing and learn nothing.

Requirements: git, curl, tar, Node 20+, and at least one supported agent, logged in. thinker ranker shows the configured ranking mode.

The knowledge cache

What a note is

A note answers a recurring question about the repository, not "what this file does". It is 3 to 12 lines with file:Symbol pointers into the code, and it comes in four kinds:

KindWhat it answers
ruleWhat a change must respect: an invariant, a convention, a trap, a fix not to undo and why.
mapWhere a recurring concern is handled, how control or data flows across files, the shape of a module area
howtoHow to build, test, run or lint, with the non-obvious flags
behaviorA rule a design document checked into the repository states, or one a person wrote down; listed by thinker system

Each note stores its title, the questions it answers, its body, the files and symbols it rests on with their content hashes, its source (a session, a pull request, a person), its confidence and its status. A note's pointers are its dependencies: a note about AuthManager.verifyToken hashes that definition alone, so it does not go stale because another method in the same file changed.

Keeping it current

A cache that drifts from the code is worse than none. Thinker keeps itself correct in three ways, all in the background, under a daily token cap (maintain.dailyTokens in the configuration):

It learns from every session

  • Each session is distilled once, when it ends, through the agent's own login: up to three new notes, and a verdict on every note it was served. confirmed (the agent acted on it) raises confidence; contradicted (the trace shows a claim was wrong) corrects the body and keeps the history; unused lets it decay. Near-duplicates are merged. A quiet session with nothing to learn from is skipped.
  • Newly merged pull requests are mined as they land, fixes first, when maintain.prs is on in the configuration (off by default: the cache grows from the sessions).
  • People add notes too: thinker add takes one you wrote, and telling your agent to remember something makes it a note when the session is distilled.

It knows when a note is stale

  • Every serving re-hashes the dependencies of every note against your working tree, uncommitted edits included. A note whose code changed is marked stale and names exactly what changed.
  • A stale note is never served by the hooks. It is held back, re-verified in the background, and served again once it is fresh. orient and lookup called by the agent still return it, under a ⚠ STALE banner.
  • Verification sends the note, the diff of its changed dependencies and their current text to a small model, which answers still_valid, update (body rewritten, history kept) or invalid (retired).
  • The block is found by a tree-sitter parser for Python, JavaScript, TypeScript, Go and Rust, which comes with the install. Other languages, and code the parser cannot read, use a regex heuristic.

It maintains itself

Maintenance runs from the prompt hooks and after every commit or merge, and spends little by default: one verification batch every three days, of the stale notes served in the last three days (at most 50), retrieval phrasings for new notes, and the removal of notes nobody was served in 14 days (a committed note is archived instead). Mining pull requests, reading design documents and carding skill files in the background are off unless the repository's maintain configuration turns each on. What a run did is shown once at the end of the next turn. thinker maintain --dry previews the next run; thinker verify re-checks stale notes now.

Local by default. Learned notes live in .thinker/local/, which git ignores. thinker export and thinker import back a cache up and restore it, checked against the checkout it lands in.

Skills

A skill is a file (SKILL.md) an agent pulls into its context by name: how to deploy, how to run the tests here, how to add a webhook. Its instructions rest on code that moves, so a skill decays the way a note does. Thinker treats the skill files checked into a repository as cached knowledge; it never edits one.

  • Each skill gets a card. A skill file under .claude/skills, .agents/skills, .codex/skills, .cursor/skills, .github/skills or skills/ gets a note of kind skill: what it is for, when to invoke it, what it prescribes, with pointers at the code it talks about. A build cards them all, and thinker skills scan cards new and changed files (maintenance does too with maintain.skills on). A served card tells the agent to invoke the skill for the full instructions.
  • A card is served like any note. The hooks and orient rank it with the rest, so a request the skill is about brings the card with its pointer to the file; nothing has to be asked for.
  • Each card is audited against the code. When code a skill talks about changes, the audit reads the file against the current code and asks one question: does the code contradict something the skill states? A skill the code contradicts is out of date: its issues are recorded, it is not served, and no further model call is spent on it until the file changes or a person marks it reviewed (thinker skills review <id>).
  • Sessions grade them. A session that invoked a skill is read for whether the skill held; a contradiction the session found takes the skill out the same way. Among skills that do the same thing, the one the sessions confirm is the one served (thinker skills prefer <id> picks by hand).
thinker skills                      # every skill with its state, evidence and issues
thinker skills scan                 # card new or changed skill files now
Efficient coding

In a session

Nothing changes in how you work. The hooks put the right note in front of the agent at the right moment, and the agent starts at the code it needs instead of searching for it.

  • Each request gets the note that fits it, with file:Symbol pointers into the code and a [6 call sites in 3 files] tag on each symbol it names. A local ranking model reads the request with the best lexical candidates and serves up to two notes, only those it scores relevant; when it is missing, notes are ranked by words alone. A note is served once per session, never while stale, and not at all for a one-word turn of conversation. When nothing fits, nothing is served.
  • Each file the agent edits brings the rules resting on it, so a trap on that code is in front of the agent as it changes it.
  • At the end of each turn one line says what was served: 🧠 thinker: 2 notes this turn (pointing at 2 files, ~7k tokens of code). It does not say "saved": whether the agent acted on a note is known only once the session is assessed.

Measured on real tasks with and without thinker, every model tested used 18% fewer input tokens per task and finished 10% sooner. .

The MCP server

The notes reach the agent through the hooks alone. The MCP server offers the agent no tools (since 2026-10-22; the orient, lookup, remember and feedback tools are gone): it carries thinker's own questions and, in a desktop app, its learning queue. For a person the command line keeps thinker lookup "<question>", thinker find and thinker drilldown.

Measure it yourself

Usage and the holdout

thinker usage summarizes how the cache has been used on this machine: notes served and how, what the sessions did with them, what learning and maintenance cost in tokens, and an estimate of the reads avoided. --here limits it to this repository, --days 7 to a period, --json gives the data. The same numbers, with the notes your agents saw most, are under Cache in thinker ui; where the context itself goes is the Context page.

One number in it is measured rather than estimated. The hooks serve nothing in 15% of prompts, chosen by a hash of the session id and the turn's number, and what every turn cost is recorded from the session's transcript. The holdout section compares the prompts that got notes with the ones that had notes withheld, as cost per prompt overall and per model, once twenty prompts stand on each side. This is what the notes do for your own work, on your own repository, by your own agent. holdout in the config changes the share or turns it off.

In the environment, THINKER_NO_LEARN=1 turns learning and maintenance off, THINKER_HOOKS=off silences the hooks, THINKER_MCP=off makes the MCP server offer no tools, and THINKER_LLM picks the agent that answers model calls (claude, codex, cursor, gemini, anthropic with ANTHROPIC_API_KEY, or openai: any OpenAI-compatible endpoint named by THINKER_LLM_BASE_URL, with the token in the variable THINKER_LLM_API_KEY_ENV names and the model in THINKER_LLM_MODEL).

Privacy and telemetry

Thinker sends pseudonymous daily effectiveness metrics (cache hit rate, note count, estimated token savings, and the totals of the holdout comparison: prompt counts and summed tool calls and tokens of prompts with and without notes) to monitor cache quality. These telemetry reports contain no code, note bodies, prompt text, file paths or repository URLs. Note ranking runs on your machine. Learning and verification use your configured model provider. The telemetry opt-out below does not disable those model calls. 

# Opt out in your shell environment:
export THINKER_TELEMETRY=off

# Or in .thinker/config.json:
{ "telemetry": false }
FAQ

Frequently asked questions

Where is my data stored? Does anything leave my machine?

The cache lives in the repository it describes, and it stays on your machine. Notes are under .thinker/local/, which git ignores; there is no team sharing or sync. Notes that an older version committed under .thinker/notes/ are still read. .thinker/config.json holds the configuration. Per machine, ~/.thinker/ holds the installed app, the usage log every serving is recorded in, and the ranking model. The Context report is read from the transcripts your agents already write; nothing is copied out of them.

Three things leave the machine, and nothing else:

  • Model calls go to the provider you already use for your agent. Learning and verification run through your agent's own login (claude, codex, gemini, cursor, or an Anthropic API key), or, in a desktop app (Claude Desktop, the Codex app, Cursor), through the app's own session. A session is distilled from a condensed transcript; verification sends a note with the diff of the code it rests on. Thinker runs no model and stores nothing of its own in the cloud.
  • Telemetry is counts only. An hourly report carries numbers: notes served, verdicts, token totals, the sums of the holdout comparison, with an install id and a hashed device id. It contains no code, note bodies, prompt text, file paths or repository URLs. THINKER_TELEMETRY=off or { "telemetry": false } in the config stops it; see Privacy and telemetry.
  • The ranking model is downloaded once at install (about 23 MB) and runs on your machine. Ranking never calls a service.

The local page of thinker ui listens on 127.0.0.1 only.

A repository with sensitive content can be turned off with thinker disable inside it. Thinker then does nothing there, in any clone or worktree: the hooks and the MCP server serve nothing, no session is distilled, and nothing is written into it. thinker enable turns it back on.

Where do the context savings come from? Why does a short section matter?

Every model call sends the whole context again: the instruction file, the catalog of skills and tools, and every tool result so far. A session of 40 calls reads a 3k-token section 40 times, 120k input tokens, and a file read on the fifth call is paid on the 35 calls after it. That is why the fixed part of the context is most of what a session spends, and why cutting a few thousand tokens from it is worth more than the number suggests: the cut applies to every call.

Thinker works on that in four places, each measured on your own sessions on the Context page:

  • Instruction sections no session acts on: compressed to a third or removed, as a diff you apply, or kept out of a trimmed copy for this checkout.
  • Skills, MCP servers, plugins and built-in tools sessions never call: switched off for the repository in the agent's own settings.
  • Tool outputs: a whole-file read, a test log or a big search trimmed to what the agent was looking for before the model reads it, so every later call reads less too.
  • The cache: a note that points at the right definition replaces the searches and whole-file reads the agent would have made to find it.

The saving shown for a cut is its tokens times the calls of the sessions that would have read it, from the transcripts. The cache's effect is measured separately, by the holdout.

Will my agent miss something I cut?

It can, which is why nothing is cut without you. The page is built so that you see the risk before taking it:

  • Use is measured first. A section is applied when a session touched its files, ran its command or read the code it names; a judge can add relevant and followed. Only a part used in under half the sessions is flagged, and high waste means large and used in almost none. Start there.
  • Compress keeps the rules. The model is told to keep every instruction, command, flag, default and path and to drop history, numbers and rationale, and you read the diff before Apply. If a section holds rules the agent must follow, compress it rather than remove it.
  • The trimmed copy leaves the team's file alone. It is the kept sections verbatim, in a file git ignores, rewritten when AGENTS.md changes. A teammate's checkout reads the full file as before.
  • A switched-off skill still runs when you type /name; only its listing leaves the context. An MCP server or plugin is off for new sessions in this repository, not removed.
  • Afterwards, followed and missed on the cards show whether sessions kept a rule they no longer read. Every cut is undone with one command (below).

No benchmark is claimed for the cuts yet: the savings are tokens the sessions would not have read, measured on your sessions, and the followed and missed counts are the check on correctness.

Can compressing tool outputs break what the agent does?

Compression changes what the model reads of a result, not what the tool did. The file is unchanged, the test ran, the search ran. What is replaced, and what is kept:

  • Only three shapes are trimmed, in Claude Code, for the tools you choose: a whole-file read, a test run and a large search. Everything else passes untouched, and so does a file under 120 lines, a file with nothing to centre on, or one where the kept lines would reach 60% of it.
  • The omitted parts are named. A trimmed file read says which line ranges were left out, which definitions they hold, and how to read any of them back. If the agent needs an omitted range it reads it; the cost of a wrong guess is one more read, not a missed fact.
  • Nothing is lost. A summarized test run keeps its full log under .thinker/state/tests/ and says where. A grouped search keeps every file that matched.
  • It is a setting, per tool, off by default. No compression on the page or --level off turns it off for the next tool call; a conversation already running is not rewritten.

What to watch: if the agent reads trimmed files back whole, the saving shrinks. The Tool outputs cards show the cost per tool after the change, on your sessions.

How does the cache work? What does it do to make my agents faster?

A note is a short rule, map or how-to about one part of the code, with file:Symbol pointers and a hash of the code it rests on. The cache is a set of such notes, and the work is in putting the right one in front of the agent without being asked:

  • On each request a hook picks the lexical candidates, then a local ranking model reads the request against them and serves up to two notes, only those it scores relevant. The agent starts at the code instead of searching for it.
  • On each file edit the rules resting on that file are served, so a trap on that code is in view while it is changed.
  • On demand, the MCP tool lookup answers one open question or fetches a note the hook listed; skill cards are among the notes.
  • Never stale. Every serving re-hashes the dependencies of every note against your working tree. A note whose code changed is held back, re-verified with the next batch (every three days), and served again once it is fresh.
  • Once per session. A note is served once, not for one-word turns, and not at all when nothing fits.

The cache keeps itself: each session is distilled once when it ends, and a maintenance batch every few days re-verifies the stale notes sessions were served and drops the ones nobody was served in two weeks. See Keeping it current.

Where do the notes come from? Can I build the cache up front?

From your own sessions, and from nothing else. When a session ends, a model reads a condensed transcript of it (what was asked, read, run and changed) and saves what the session worked out that the next one would otherwise work out again, usually nothing or one note. The same call grades the notes the session was served: confirmed, contradicted (the note is corrected) or unused. A quiet session, with nothing served, no edit, no failure and little exploring, is skipped.

  • There is no build step. thinker setup connects your agents and nothing else; every git repository starts with an empty cache, and the hooks serve from it once it holds a few notes.
  • The spend is bounded. One model call per session, through your agent's login, and learning and maintenance together stop at a daily token cap (maintain.dailyTokens in .thinker/config.json).
  • You can add your own. thinker add takes a note you wrote, and telling your agent to remember something makes it a note when the session is distilled.
  • You can stop it. { "learn": { "sessions": false } } in the config stops learning from sessions in a repository; THINKER_NO_LEARN=1 stops all learning.

How can I tell if Thinker is helping my agents?

  • At the end of each turn one line says what was served and the code it pointed at. It does not say "saved": whether the agent acted on a note is known only once the session is assessed.
  • The Context page, and thinker context, show where your agents' context goes: what each instruction section, skill and tool costs a session and how often sessions acted on it, so what you cut is measured on your own sessions.
  • thinker usage, and the usage under Cache in thinker ui, show notes served, what the sessions did with them (confirmed, contradicted, unused), what learning and maintenance cost in tokens, and an estimate of the reads avoided.
  • The holdout is measured, not estimated. 15% of prompts are served nothing, chosen by a hash of the session and the turn, and what every turn cost is read from the session's transcript. Once twenty prompts stand on each side, the holdout section compares the cost per prompt: tool calls and tokens with notes against without, on your repository, by your agent.

A note served is not a note used. Read the confirmed and unused counts rather than the hit rate; a cache that serves often and is rarely acted on is costing tokens, and maintenance archives such notes over time.
