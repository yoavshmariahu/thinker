A knowledge cache to help you catch regressions and boost coding agent efficiency

Thinker’s model-agnostic knowledge cache works across coding models and agents. It uses frontier models to build and maintain knowledge from code, sessions, and merged pull requests, and a small local ranking model to choose which notes to serve. Dependency-based invalidation and verification keep the cache fresh, helping agents catch regressions and complete tasks with fewer tokens.

How it fits together

1

Build

thinker setup builds the cache from merged pull requests, fixes first.

2

Use

Hooks hand the agent the note that fits each request. thinker review checks a change against the notes before it merges.

3

Keep current

Sessions and merged pull requests become notes. A note whose code changed is held back and re-verified. Nothing is run by hand.

Everything lives under .thinker/ in the repository. Notes are keyed to the exact definitions they describe by content hash, so the cache knows when the code under a note has moved and never serves a claim it cannot stand behind.

Install and set up

The install command from the landing page installs the tool under ~/.thinker and wires it into the agents on this machine, once, in their own settings. Run from inside a repository, it also sets that repository up. Anywhere else, run thinker setup inside a repository later. 

# Connect the agents, then ask whether to build the cache
thinker setup

# Build now: choose Full repo or Specify project directories; then mine merged PRs (--prs n, default 60);
# --areas n also has your agent explore n source areas
thinker setup --build

# Wire things up only; the cache grows from your sessions
thinker setup --no-build

Working in a large repository? Setup offers Full repo or Specify project directories. Enter a project name and comma-separated directories such as apps/web, packages/ui. Thinker saves thinker.project.json and estimates the build for your selection. The installer offers the same choice. 

# Or save a project before onboarding
thinker project init apps/web packages/ui --name "Web app"
thinker seed --dry # preview selected exploration areas
thinker setup --build --yes

setup, seed, and mine-prs reuse the saved project. Use --project other.project.json for another selection or --full-repo for one full-repository run. Paths are relative to the repository root. Exploration and history mining focus on the selected directories; retrieval, review, and ongoing learning still use the whole repository cache.

Building runs through your agent's own login: about 5.5M tokens and twenty minutes with the defaults, most of them cached prompt reads. The estimate is printed in tokens and minutes before anything runs, never in dollars, since most agents run on subscriptions.

The wiring is machine-wide, the cache is per repository. Hooks and the MCP server are present in every checkout and act only in one that thinker setup has set up. Elsewhere your agents are served nothing and learn nothing.

Requirements: git, curl, tar, Node 20+, and at least one supported agent, logged in. thinker ranker shows the configured ranking mode.

The knowledge cache

What a note is

A note answers a recurring question about the repository, not "what this file does". It is 3 to 12 lines with file:Symbol pointers into the code, and it comes in four kinds:

KindWhat it answers
ruleWhat a change must respect: an invariant, a convention, a trap, a fix not to undo and why. The kind a review draws on most.
mapWhere a recurring concern is handled, how control or data flows across files, the shape of a module area
howtoHow to build, test, run or lint, with the non-obvious flags
behaviorA desired behavior of the system a person wrote down; the code must uphold it (see Desired behaviors)

Each note stores its title, the questions it answers, its body, the files and symbols it rests on with their content hashes, its source (a session, a pull request, a person), its confidence and its status. A note's pointers are its dependencies: a note about AuthManager.verifyToken hashes that definition alone, so it does not go stale because another method in the same file changed.

Building the cache

thinker setup --build fills the cache from merged pull requests, and prints what it will cost in tokens and minutes before spending anything. Ctrl-C stops it at any time and keeps every note saved so far; the cache keeps growing from your sessions and a few merged pull requests per background run.

  • Merged pull requests, fixes first. Up to 60 of them are distilled into rules: what the symptom was, what the fix changed, and what a later change must not undo. The record of a fix is what a review draws on most. Every pull request looked at is recorded in .thinker/prs.json, so none is distilled twice.
  • Exploration sessions, only when asked. With --areas n (or thinker seed) the source is grouped into areas by size and structure, an agent is sent through up to n of them, and what it worked out is distilled into maps and howtos. It costs far more per note than mining, so a build leaves it out by default.
thinker setup --build --prs 100 --areas 20   # more history, and explore 20 areas
thinker mine-prs                             # later: go further back through merged pull requests, 20 at a time
thinker mine-prs --git --fixes               # no GitHub: fix commits from git history

A build also drafts desired-behavior candidates from the strongest rule notes for a person to accept or discard (thinker system propose). Without a build, the cache starts empty and grows from your sessions.

Keeping it current

A cache that drifts from the code is worse than none. Thinker keeps itself correct in three ways, all in the background, under a cap of 2M tokens a day:

It learns from every session

  • Each session is distilled once, when it ends, through the agent's own login: up to three new notes, and a verdict on every note it was served. confirmed (the agent acted on it) raises confidence; contradicted (the trace shows a claim was wrong) corrects the body and keeps the history; unused lets it decay. Near-duplicates are merged. A quiet session with nothing to learn from is skipped.
  • Newly merged pull requests are mined as they land, fixes first, so the next review already knows about the last fix.
  • Agents and people add notes too: the remember tool, thinker add, and thinker system add for a desired behavior.

It knows when a note is stale

  • Every serving re-hashes the dependencies of every note against your working tree, uncommitted edits included. A note whose code changed is marked stale and names exactly what changed.
  • A stale note is never served by the hooks. It is held back, re-verified in the background, and served again once it is fresh. orient and lookup called by the agent still return it, under a ⚠ STALE banner.
  • Verification sends the note, the diff of its changed dependencies and their current text to a small model, which answers still_valid, update (body rewritten, history kept) or invalid (retired).
  • thinker ast install adds tree-sitter grammars (Python, JavaScript, TypeScript, Go, Rust) for exact symbol boundaries; otherwise a regex heuristic finds the block.

It maintains itself

Maintenance runs from the prompt hooks and after every commit or merge, at most once every four hours: it re-verifies up to 10 stale notes (the recently served first), mines up to 3 newly merged pull requests, writes retrieval phrasings for new notes, and archives notes the sessions showed are not worth serving. What a run did is shown once at the end of the next turn. thinker maintain --dry previews the next run; thinker verify re-checks stale notes now.

Local by default. Learned notes live in .thinker/local/, which git ignores. thinker export and thinker import back a cache up and restore it, checked against the checkout it lands in.
Code Review

Reviewing a change

thinker review turns the cache around: instead of serving notes to an agent about to make a change, it checks a change against them. It runs from the command line, before a commit or on a pull request.

A review is for two things a diff alone cannot show: a change that undoes a fix the repository already made, and a change that breaks a convention or a desired behavior the cache holds. Across 100 tests in seven open-source repositories, each a fix reversed so the change brings its bug back, review with Thinker missed 73% fewer bugs than the same model without it. The cache had learned the fixes being tested. The benchmark modal shows the results by model and explains the scoring. 

thinker review                      # the working tree against HEAD
thinker review --staged             # what is about to be committed
thinker review --base origin/main   # the branch since its merge base
thinker review --ref <commit>       # one commit, read from git alone
thinker review --state src/auth/    # no change: the current code against the notes on it

It makes two model calls and merges what they find: one sees the diff and the code it touched, as any reviewer would; the other sees the notes resting on the changed code and the notes that bear on it. Every finding carries a file, a line, the evidence it rests on and the note it came from. Findings that are the same problem seen from several notes are reported once.

  • The cache is evidence, not truth. A note that already disagreed with the code before the change is reported as drift of the cache, never charged to the change. Nothing in the cache is rewritten by a review.
  • It says where it is blind. When most of the changed files carry no note, the review says so first: there it is the model reading the diff alone, and "no findings" is not a clean bill.
  • Removed definitions still referenced are reported without a model call.

--kinds behavior consults the desired behaviors alone, --dry makes no model call, --json gives the report as data, --model picks the model (reviewModel in the config, default sonnet).

Proof of correctness

Agent-written code arrives with a diff and a claim that it works. A reviewer has to ask three more things: what the agent set out to do and why, how that was tested, and what the repository already knows that the agent did not. Thinker posts the answers as one comment on the pull request, from your own GitHub login, each part marked by where it came from: the agent, the test runner, the cache, or a model's reading.

The report below is a real one, produced by the command at the end of this section on a small demonstration repository. The change makes auto-pause react within two seconds of the runner stopping, instead of five. Both named tests passed. The cache remembered why the old detector waited: under a bridge the GPS reports zero speed with no fix, and that paused people's runs in every tunnel.

What each part rests on

supplied by the agent

The agent's intention. With the run the agent sends a task: the request, its reason for the approach, the steps it meant to take, its open questions, and acceptance criteria linked to named tests (task.json). Thinker anchors each step to a changed line, so the intention is checked against the diff rather than taken on trust, and the review says where no anchor was found.

observed by the runner

How it was tested. The checks are the commands committed in .thinker/verification.json on the base branch, run in Docker on a frozen snapshot of the candidate; thinker's reporter records each named test as passed, skipped or failed and matches it to the criterion it was linked to. The candidate cannot replace its own checks, and a skipped or missing test is called out, not quietly counted as a pass.

from the cache

What the repository already knows. Notes mined from merged fixes and earlier sessions rest on the changed definitions, and desired behaviors written by the team are held against the change. A finding names the note and the pull request it was learned from. In the report above both tests are green and the diff reads as a tidy simplification; only the cache knew that the filter it removed was the fix for runs pausing in tunnels.

model reading

Labeled, never silent. Wherever a model read a line of the diff or an assertion, the review says so. An observed pass is a fact about the snapshot; whether its assertions cover the request is a judgment, and the review leaves that judgment, under Before approving, to the reviewer.

Run it and post the evidence

First, commit .thinker/verification.json on the trusted base. This contract pins the Docker image and required check commands; a candidate cannot replace its own evaluation commands. Docker, a configured review model, and an authenticated GitHub CLI (gh auth login) are required for this flow.

Example execution contract

Save as .thinker/verification.json and commit it to the base branch. Replace the image placeholder with an actual image digest containing Node and your project’s system dependencies. This example allows network access for npm ci.

{
  "version": 1,
  "image": "your-registry/verification@sha256:<64-character-image-digest>",
  "platform": "linux/amd64",
  "network": "bridge",
  "setup": "npm ci",
  "checks": [{
    "id": "unit",
    "command": "node --test --test-reporter=/thinker/reporter.mjs test/*.test.js",
    "reporter": "node",
    "timeoutSeconds": 600
  }]
}

Each required check runs in a fresh container. The Node reporter records named test results. A setup failure, timeout, or missing report leaves verification incomplete.

Save the request and links to existing tests as task.json. Test names and paths must match your repository:

{
  "request": "Pause a run within two seconds of the runner stopping; resume when they move",
  "rationale": "Two GPS samples under 0.5 m/s are enough to tell a stop from a slow stride",
  "intendedChanges": [
    "Shorten the stop window from five samples to two",
    "Resume on the first moving sample"
  ],
  "questions": ["Should the window stay at five for watches sampling GPS at 0.5 Hz?"],
  "criteria": [{
    "text": "A run pauses within two seconds of the runner stopping",
    "tests": [{ "check": "unit", "name": "pauses within two seconds of a stop", "file": "test/autopause.test.js" }]
  }, {
    "text": "A paused run resumes when the runner moves",
    "tests": [{ "check": "unit", "name": "resumes on the first moving sample", "file": "test/autopause.test.js" }]
  }]
}
thinker review --run --base origin/main --task task.json \
  --pr 318 --post

--run waits for the checks and code assessment, then --post adds the report as a PR conversation comment through your GitHub login. Run this in the PR’s checkout: --pr identifies the destination, it does not select the code to review. Each invocation adds a new comment.

To keep working while checks run, use --start, then post the result with thinker review --status <run-id> --pr 318 --post. If the code or other tracked inputs have changed, the report marks the evidence as outdated. Full check logs stay local and are not uploaded.

What the proof establishes

A named test pass establishes that the test ran successfully on the captured snapshot. Thinker labels its reading of the assertions and code as a model assessment, and calls out skipped or unobserved tests, missing criterion coverage, and possible weakening of test or CI gates. The reviewer decides whether that evidence covers the request.

This is practical correctness evidence with an explicit scope. It is not a mathematical proof, a signed CI attestation, or a guarantee that every edge case is covered. Ordinary thinker review --post posts a code assessment without executing tests; use --run or a completed verification run for execution evidence. Your existing CI checks still apply.

In CI and before commits

--strict exits 2 on an error-severity finding, so a review can gate a pull request. --pr n --post posts the report as a comment on the pull request through your gh login. 

# In a CI job on a pull request branch, after thinker setup has run on the checkout:
thinker review --base origin/main --strict
thinker review --base origin/main --pr 142 --post   # and comment on the pull request

For a check before every commit, turn it on per checkout; the pre-commit hook then runs thinker review --staged --strict and blocks the commit on an error-severity finding, warnings alone do not: 

git config --local thinker.reviewBeforeCommit true

A review uses your configured model and adds latency and tokens to each commit, so it is off unless you turn it on. thinker impact connects reviews and recorded agent work to the pull requests they went into: tokens per pull request, and findings confirmed as bugs fixed before merge.

Desired behaviors

Every other kind of note is a claim about the code, and when they disagree the note yields. A behavior note is the other way round: a person writes down what the system must do and where that is upheld, and from then on a change must conform, or be called out for not conforming. 

thinker system                      # every behavior, and whether the code upholds it
thinker system add file.json --fixed
thinker system promote <id>         # a rule the cache already holds becomes a behavior
thinker system propose              # drafts from the build, and rules worth promoting
thinker system md                   # write them as .thinker/SYSTEM.md
thinker ui                          # accept, edit or discard them in the browser

A fixed behavior makes a change that stops upholding it an error, with the behavior quoted in full at the top of the review. A mutable one is a warning, and may be revised by a change that edits the note itself. Before a merge the behavior is the truth; once the change is merged, the behavior is revised to match the code, with the old text in its history. Agents can propose one with remember (listed as proposed until thinker system accept) and read them all with lookup and kind: "behavior".

Efficient coding

In a session

Nothing changes in how you work. The hooks put the right note in front of the agent at the right moment, and the agent starts at the code it needs instead of searching for it.

  • Each request gets the note that fits it, with file:Symbol pointers into the code and a [6 call sites in 3 files] tag on each symbol it names. A local ranking model reads the request with the best lexical candidates and serves one note, only when it scores it relevant; when it is missing, notes are ranked by words alone. A note is served once per session, never while stale, and not at all for a one-word turn of conversation. When nothing fits, nothing is served.
  • Each file the agent edits brings the notes resting on it, rules first, so a trap on that code is in front of the agent as it changes it.
  • At the end of each turn one line says what was served: 🧠 thinker: 2 notes this turn (pointing at 2 files, ~7k tokens of code). It does not say "saved": whether the agent acted on a note is known only once the session is assessed.

Measured on real tasks with and without thinker, every model tested used 18% fewer input tokens per task. .

Tools the agent can call

Beyond what the hooks serve, the MCP server gives the agent the cache and the code graph on demand:

ToolWhat it does
orientUp to five notes for a task, with the code behind the main pointers, and the notes it did not serve listed by title
lookupOne specific question, or a note by id; kind: "behavior" for the desired behaviors
findThe definitions whose name or body carry the words of a query, as pointers with their lines, when no note answers it
drilldownA definition whole, with one hop of callers and callees and the notes resting on it
remember, feedbackSave a note the agent worked out; confirm or correct one it was served

The same tools exist on the command line (thinker orient "<task>", lookup, find, drilldown). The first prompt of a session tells the agent that find and drilldown exist and how to load them.

Measure it yourself

Benchmark in your repo

You do not need to take the benchmarks on faith. Thinker can run the same paired comparison on your own repository: 

# A recent merged pull request, with and without the cache
thinker benchmark pr [number]

# A question the cache covers (Enter takes the first), or your own
thinker benchmark run "how are permissions checked on project exports"

# The latest comparison again
thinker benchmark report

It makes two read-only agent calls, one without thinker and one with the relevant notes, and compares wall time, turns, tool calls and tokens side by side. Both answers are saved under .thinker/benchmarks/ so you can judge their quality yourself; speed alone is not a correctness score. If the cache does not cover a question, no agent call is made and questions it does cover are offered instead.

Usage and the holdout

thinker usage summarizes how the cache has been used on this machine: notes served and how, what the sessions did with them, what learning and maintenance cost in tokens, and an estimate of the reads avoided. --here limits it to this repository, --days 7 to a period, --json gives the data. The same numbers, with the notes your agents saw most, are in the Usage view of thinker ui.

One number in it is measured rather than estimated. The hooks serve nothing in 15% of sessions, chosen by a hash of the session id so a session is held out for its whole length, and every session's cost is recorded from its own transcript. The holdout section compares the sessions that got notes with the ones that had notes withheld, as medians per model, once five sessions stand on each side. This is what the notes do for your own work, on your own repository, by your own agent. holdout in the config changes the share or turns it off.

Reference

The local page

thinker ui opens a page in your browser with three views of the cache. A dropdown at the top picks the repository, or all of them on this machine. The first thinker setup in a repository opens it for you (--no-ui leaves it closed); that page stops by itself after half an hour unused. 

thinker ui                          # opens the page; Ctrl+C stops it
thinker ui --port 4800 --no-open    # a fixed port, without opening a browser
ViewWhat it shows
UsageWhat thinker usage reports, over 7 days, 30 days or all time: notes served, what agents acted on, what was learned, the tokens it cost, the holdout comparison, and the notes your agents saw most
CacheEvery note, filtered by status and kind, searched and sorted by hits or age, with the code it points at and where it came from; archive a note or restore it to serving
System behaviorsThe desired behaviors, filtered by proposed, active, blocking, warn only, or broken or unverified; accept a proposed one as written or as blocking, edit it, or discard it

The page listens on 127.0.0.1 only, every request carries a token minted for that run, and it reads and writes nothing but this machine's cache.

Configuration

Everything in .thinker/config.json is optional.

KeyEffect
learn{"sessions": false} stops distilling sessions; pull requests and re-verification go on
maintainenabled, dailyTokens (2,000,000), verifyPerRun (10), phrasePerRun (8), prsPerRun (3)
archivekinds and unservedDays (30), or false
holdoutThe share of sessions served nothing (0.15; 0 or false: none)
ceThe local ranker the hooks choose notes with: floor (0), maxNotes (1), or false to rank by words alone
snippets, noticefalse: no code behind the pointers; no end-of-turn line
distillModel, verifyModel, reviewModelThe model for each kind of call
telemetryfalse: no metrics sent

In the environment, THINKER_NO_LEARN=1 turns learning and maintenance off, THINKER_HOOKS=off silences the hooks, THINKER_MCP=off makes the MCP server offer no tools, and THINKER_LLM picks the agent that answers model calls (claude, codex, cursor, gemini, or anthropic with ANTHROPIC_API_KEY).

Privacy and telemetry

Thinker sends pseudonymous daily effectiveness metrics (cache hit rate, note count, estimated token savings) to monitor cache quality. These telemetry reports contain no code, note bodies, prompt text, file paths or repository URLs. Note ranking runs on your machine. Learning, verification and review use your configured model provider. The telemetry opt-out below does not disable those model calls. 

# Opt out in your shell environment:
export THINKER_TELEMETRY=off

# Or in .thinker/config.json:
{ "telemetry": false }
