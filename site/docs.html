Think ahead. Save context.

Every model call your coding agent makes re-reads the same things: the instruction file, the skill list, every MCP server's tool definitions, every tool result so far. Most of it is never acted on. Thinker shows you where the context goes, part by part, and lets you cut the parts your sessions do not use.

  • See it. The Context page reads your agents' own session transcripts and shows input tokens a session split into instruction files, skills, MCP servers, plugins, built-in tools and tool outputs, for one repository or all of them. Each section, skill and tool stands beside what it costs and how often sessions acted on it, with the waste flagged.
  • Cut it. Compress or remove instruction sections as a diff you apply; keep only the sections that matter in a trimmed copy for this checkout; switch unused skills and tools off from the next session, with a backup; compress long tool outputs before the agent reads them. Every cut is shown first and undone with one command.
  • Remember instead. The knowledge cache: what your agent works out in a session becomes a short note pinned to the code it describes, served on the requests it fits and re-checked when that code changes, so the agent reads less to find its way.

How it fits together

1

Learn

Pick repositories on the local page; each cache is built from merged pull requests, fixes first, and skill files get cards.

2

Inject

Hooks rank the notes against each request and hand the agent the ones that fit, plus the rules on each file it edits.

3

Keep fresh

Sessions grade what was served and add what they learned. A note whose code changed is held back and re-verified. Nothing is run by hand.

Everything lives under .thinker/ in the repository. Notes are keyed to the exact definitions they describe by content hash, so the cache knows when the code under a note has moved and never serves a claim it cannot stand behind.

Where the context goes

The Context page

thinker ui opens on it; thinker context prints the same report in the terminal (--days 7, --json). Everything is read from the agents' own session transcripts on this machine. Nothing is sent anywhere, and the report changes nothing by itself: every cut is a choice you make, shown first, undone with one command.

What it shows

Input tokens over time, as stacked columns by day or week, total or per session, split into the parts the agent reads on every model call. A part's cost a session is its tokens times the session's model calls: a 4k-token instruction file read by 40 calls is 160k input tokens, and that is the number the page sorts by.

PartWhat it isRead from
Instruction filesAGENTS.md, or CLAUDE.md where there is no AGENTS.md, section by sectionClaude Code, Codex, Cursor and Gemini CLI sessions
Custom toolsThe skills listed in every session, MCP servers and plugins, with their descriptions and tool definitionsClaude Code in full; Codex's skill catalog and MCP namespaces; Cursor's MCP servers
Built-in toolsThe agent's own tool definitions, re-sent with every callClaude Code
Tool outputsWhat each tool's results added to the conversation, re-read by every call after themClaude Code

One part at a time, as cards. Each instruction section, skill and tool beside its cost (tokens a call, input tokens a session) and its use. A section is applied when a session touched its files, ran its command or read the code it names, free, from the transcript; relevant and followed come from a model reading one session against the sections, which costs tokens, so it runs when you press Judge 5 more sessions or on a sample of sessions as they end once you turn that on (instructions.value.judge in the configuration). A skill is read when a session opened it, and the sampled outcome check says whether the sessions that read it kept its rules, and how often one broke them without reading it. A tool is used when a session called it. Waste is high or medium for a part the sessions used in under half of them and that costs a large share of its kind; the saving beside it is what cutting it would save at most.

Cut what no session acts on

Each section of the instruction file beside what it costs a call, how many sessions acted on it and what it cost this week. The ones no session uses are flagged; pick them and have a model compress them to a third, or remove them, as a diff you apply. Skills, MCP servers and plugins get the same treatment on their own cards: Switch off takes one out of the next session's context, in the agent's own settings, with a backup (thinker harness --undo puts it back; a skill switched off still runs as /name).

Compress what the agent reads back

A tool result stays in the conversation, so every model call after it reads it again: a whole file read is paid for twenty times over. Compression keeps the lines around what the session searched for, a test run's counts and distinct failures, a search's hits per file, and names what it left out so the agent can ask for any range.

Tokens are counted from the transcripts, at about four characters a token, times the model calls the transcript records. The outputs' cost is each result's tokens times the model calls left after it; a compaction, which drops old results, is not seen, so that part is an upper estimate. The waste flags and savings are measurements of use, not a promise: cutting a section saves its tokens, and whether the agent then misses it is what followed and missed are there to show. No benchmark is claimed for the cuts; the are about the cache.

Install and set up

The install command from the landing page installs the tool under ~/.thinker and wires it into the agents on this machine, once, in their own settings, asking nothing in the terminal. Setup itself happens in the browser: the installer ends by opening the local page on its warm-up view.

  1. Pick repositories. The page lists the git repositories your agents worked in over the last 30 days, most recent first, found from the agents' own session records, each with a build estimate in tokens and minutes. The five you used most recently are picked for you; one that already has a cache is marked and left unpicked.
  2. Choose how much to read. Per repository: Full (the newest 60 merged pull requests) or Shallow (the newest 30% of them), the whole repository or only the directories you pick. A switch on each row turns thinker off for a repository no model should read.
  3. Choose the agent and model. The bar at the top lists the agent CLIs on the machine, says whether each is signed in, and adds up the tokens and time of everything picked. A build runs through that agent's own login.
  4. Press Start building, or Skip for now. The builds run one at a time in the background, and closing the tab does not stop them. The Cache view shows each one's stage ("mining 12/60 PRs"), the notes saved so far, the time left and a Stop button; stopping keeps every note saved so far.

Every other git repository gets an empty cache with its first session and grows from there, so skipping a build costs nothing but a slower start. 

# Open the local page again any time
thinker ui
thinker ui --tab warmup             # straight to the warm-up view

# No browser, or a script: build one repository's cache from the terminal.
# A build reads merged pull requests (--prs n, default 60); it does not explore the code
thinker setup --build

What a build reads. By default, your areas: the directories your own commits touched in the last six months (your merged pull requests when the commits carry another identity), the top five, so the cache is warm where you work. Setup shows them and offers Whole repository (the generic build) and Specify project directories instead; the warm-up page starts each repository on your areas too, with the directory picker to change them. The choice is kept as areas in .thinker/config.json, which maintenance reads to keep warming the same places: new merges inside the areas, and their older history a few changes a run until each area has had its walk (100 changes). thinker usage shows the areas and how many notes point into each. A named project saves thinker.project.json and estimates the build for your selection. 

# Or save a project before onboarding
thinker project init apps/web packages/ui --name "Web app"
thinker setup --build --yes

setup and mine-prs reuse the saved project. Use --project other.project.json for another selection or --full-repo for one full-repository run. Paths are relative to the repository root. History mining focuses on the selected directories; retrieval and ongoing learning still use the whole repository cache.

Building runs through your agent's own login: roughly 700k to 900k tokens and about ten minutes with the defaults (60 merged pull requests). The estimate is shown in tokens and minutes before anything runs, never in dollars, since most agents run on subscriptions.

The wiring is machine-wide, the cache is per repository. Hooks and the MCP server are present in every git checkout, and each checkout keeps its own cache under .thinker/, started on first use and excluded from git status through .git/info/exclude. Outside a git repository your agents are served nothing and learn nothing.

Requirements: git, curl, tar, Node 20+, and at least one supported agent, logged in. thinker ranker shows the configured ranking mode.

The knowledge cache

What a note is

A note answers a recurring question about the repository, not "what this file does". It is 3 to 12 lines with file:Symbol pointers into the code, and it comes in four kinds:

KindWhat it answers
ruleWhat a change must respect: an invariant, a convention, a trap, a fix not to undo and why.
mapWhere a recurring concern is handled, how control or data flows across files, the shape of a module area
howtoHow to build, test, run or lint, with the non-obvious flags
behaviorA rule a design document checked into the repository states, or one a person wrote down; listed by thinker system

Each note stores its title, the questions it answers, its body, the files and symbols it rests on with their content hashes, its source (a session, a pull request, a person), its confidence and its status. A note's pointers are its dependencies: a note about AuthManager.verifyToken hashes that definition alone, so it does not go stale because another method in the same file changed.

Building the cache

A build, started from the warm-up view or with thinker setup --build, fills the cache from merged pull requests, and shows what it will cost in tokens and minutes before spending anything. Stopping it (the Stop button, or Ctrl-C in the terminal) keeps every note saved so far; the cache keeps growing from your sessions and a few merged pull requests per background run.

  • Merged pull requests, fixes first. Up to 60 of them are distilled into rules: what the symptom was, what the fix changed, and what a later change must not undo. Every pull request looked at is recorded in .thinker/prs.json, so none is distilled twice.
thinker setup --build --prs 100              # more history
thinker mine-prs                             # later: go further back through merged pull requests, 20 at a time
thinker mine-prs --git --fixes               # no GitHub: fix commits from git history

A build also reads the design documents checked into the repository (READMEs beside the code, design files) and saves the rules they state as behavior notes, which an agent editing the code they rest on is handed like any other rule. thinker system lists them. Without a build, the cache starts empty and grows from your sessions.

Keeping it current

A cache that drifts from the code is worse than none. Thinker keeps itself correct in three ways, all in the background, under a daily token cap (maintain.dailyTokens in the configuration):

It learns from every session

  • Each session is distilled once, when it ends, through the agent's own login: up to three new notes, and a verdict on every note it was served. confirmed (the agent acted on it) raises confidence; contradicted (the trace shows a claim was wrong) corrects the body and keeps the history; unused lets it decay. Near-duplicates are merged. A quiet session with nothing to learn from is skipped.
  • Newly merged pull requests are mined as they land, fixes first, so the next session already knows about the last fix.
  • Agents and people add notes too: the remember tool and thinker add.

It knows when a note is stale

  • Every serving re-hashes the dependencies of every note against your working tree, uncommitted edits included. A note whose code changed is marked stale and names exactly what changed.
  • A stale note is never served by the hooks. It is held back, re-verified in the background, and served again once it is fresh. orient and lookup called by the agent still return it, under a ⚠ STALE banner.
  • Verification sends the note, the diff of its changed dependencies and their current text to a small model, which answers still_valid, update (body rewritten, history kept) or invalid (retired).
  • The block is found by a tree-sitter parser for Python, JavaScript, TypeScript, Go and Rust, which comes with the install. Other languages, and code the parser cannot read, use a regex heuristic.

It maintains itself

Maintenance runs from the prompt hooks and after every commit or merge, at most once every four hours: it re-verifies up to 10 stale notes (the recently served first), mines up to 3 newly merged pull requests, writes retrieval phrasings for new notes, and archives notes the sessions showed are not worth serving. What a run did is shown once at the end of the next turn. thinker maintain --dry previews the next run; thinker verify re-checks stale notes now.

Local by default. Learned notes live in .thinker/local/, which git ignores. thinker export and thinker import back a cache up and restore it, checked against the checkout it lands in.

Skills

A skill is a file (SKILL.md) an agent pulls into its context by name: how to deploy, how to run the tests here, how to add a webhook. Its instructions rest on code that moves, so a skill decays the way a note does. Thinker treats the skill files checked into a repository as cached knowledge; it never edits one.

  • Each skill gets a card. A skill file under .claude/skills, .agents/skills, .codex/skills, .cursor/skills, .github/skills or skills/ gets a note of kind skill: what it is for, when to invoke it, what it prescribes, with pointers at the code it talks about. A build cards them all; maintenance cards new and changed files as they land. A served card tells the agent to invoke the skill for the full instructions.
  • A card is served like any note. The hooks and orient rank it with the rest, so a request the skill is about brings the card with its pointer to the file; nothing has to be asked for.
  • Each card is audited against the code. When code a skill talks about changes, the audit reads the file against the current code and asks one question: does the code contradict something the skill states? A skill the code contradicts is out of date: its issues are recorded, it is not served, and no further model call is spent on it until the file changes or a person marks it reviewed (thinker skills review <id>).
  • Sessions grade them. A session that invoked a skill is read for whether the skill held; a contradiction the session found takes the skill out the same way. Among skills that do the same thing, the one the sessions confirm is the one served (thinker skills prefer <id> picks by hand).
thinker skills                      # every skill with its state, evidence and issues
thinker skills scan                 # card new or changed skill files now
Efficient coding

In a session

Nothing changes in how you work. The hooks put the right note in front of the agent at the right moment, and the agent starts at the code it needs instead of searching for it.

  • Each request gets the note that fits it, with file:Symbol pointers into the code and a [6 call sites in 3 files] tag on each symbol it names. A local ranking model reads the request with the best lexical candidates and serves up to two notes, only those it scores relevant; when it is missing, notes are ranked by words alone. A note is served once per session, never while stale, and not at all for a one-word turn of conversation. When nothing fits, nothing is served.
  • Each file the agent edits brings the rules resting on it, so a trap on that code is in front of the agent as it changes it.
  • At the end of each turn one line says what was served: 🧠 thinker: 2 notes this turn (pointing at 2 files, ~7k tokens of code). It does not say "saved": whether the agent acted on a note is known only once the session is assessed.

Measured on real tasks with and without thinker, every model tested used 18% fewer input tokens per task and finished 10% sooner. .

Tools the agent can call

Beyond what the hooks serve, the MCP server gives the agent the cache on demand:

ToolWhat it does
orientUp to five notes for a task, with the code behind the main pointers, and the notes it did not serve listed by title
lookupOne specific question, or a note by id
remember, feedbackSave a note the agent worked out; confirm or correct one it was served

The same tools exist on the command line (thinker orient "<task>", lookup). Two code tools, find and drilldown, are off by default: agents are neither offered them nor told about them unless thinker tools enable find drilldown turns them on in a repository.

Measure it yourself

Usage and the holdout

thinker usage summarizes how the cache has been used on this machine: notes served and how, what the sessions did with them, what learning and maintenance cost in tokens, and an estimate of the reads avoided. --here limits it to this repository, --days 7 to a period, --json gives the data. The same numbers, with the notes your agents saw most, are under Cache in thinker ui; where the context itself goes is the Context page.

One number in it is measured rather than estimated. The hooks serve nothing in 15% of prompts, chosen by a hash of the session id and the turn's number, and what every turn cost is recorded from the session's transcript. The holdout section compares the prompts that got notes with the ones that had notes withheld, as cost per prompt overall and per model, once twenty prompts stand on each side. This is what the notes do for your own work, on your own repository, by your own agent. holdout in the config changes the share or turns it off.

Privacy and telemetry

Thinker sends pseudonymous daily effectiveness metrics (cache hit rate, note count, estimated token savings, and the totals of the holdout comparison: prompt counts and summed tool calls and tokens of prompts with and without notes) to monitor cache quality. These telemetry reports contain no code, note bodies, prompt text, file paths or repository URLs. Note ranking runs on your machine. Learning and verification use your configured model provider. The telemetry opt-out below does not disable those model calls. 

# Opt out in your shell environment:
export THINKER_TELEMETRY=off

# Or in .thinker/config.json:
{ "telemetry": false }
FAQ

Frequently asked questions

Where is my data stored? Does anything leave my machine?

The cache lives in the repository it describes, and it stays on your machine. Notes, from pull requests and from sessions alike, are under .thinker/local/, which git ignores; there is no team sharing or sync. Notes that an older version committed under .thinker/notes/ are still read. .thinker/config.json holds the configuration and .thinker/prs.json the list of pull requests already read. Per machine, ~/.thinker/ holds the installed app, the usage log every serving is recorded in, and the ranking model.

Three things leave the machine, and nothing else:

  • Model calls go to the provider you already use for your agent. Learning, verification and mining run through your agent's own login (claude, codex, gemini, cursor, or an Anthropic API key). A session is distilled from a condensed transcript; a pull request is read as its title, description, review comments and diff; verification sends a note with the diff of the code it rests on. Thinker runs no model and stores nothing of its own in the cloud.
  • Telemetry is counts only. An hourly report carries numbers: notes served, verdicts, token totals, the sums of the holdout comparison, with an install id and a hashed device id. It contains no code, note bodies, prompt text, file paths or repository URLs. THINKER_TELEMETRY=off or { "telemetry": false } in the config stops it; see Privacy and telemetry.
  • The ranking model is downloaded once at install (about 23 MB) and runs on your machine. Ranking never calls a service.

gh reads merged pull requests from GitHub during mining; it posts nothing. The local page of thinker ui listens on 127.0.0.1 only.

A repository with sensitive content can be turned off on the warm-up page of thinker ui, or with thinker disable inside it. Thinker then does nothing there, in any clone or worktree: the hooks and the MCP server serve nothing, no session is distilled, no pull request is read, and nothing is written into it. thinker enable turns it back on.

How does the cache work? What does it do to make my agents faster?

A note is a short rule, map or how-to about one part of the code, with file:Symbol pointers and a hash of the code it rests on. The cache is a set of such notes, and the work is in putting the right one in front of the agent without being asked:

  • On each request a hook picks the lexical candidates, then a local ranking model reads the request against them and serves up to two notes, only those it scores relevant, with the code behind its pointers and a count of call sites for each symbol named. The agent starts at the code instead of searching for it.
  • On each file edit the rules resting on that file are served, so a trap on that code is in view while it is changed.
  • On demand, the MCP tools orient and lookup give the agent notes when the hooks served nothing; skill cards are among them.
  • Never stale. Every serving re-hashes the dependencies of every note against your working tree. A note whose code changed is held back, re-verified in the background, and served again once it is fresh.
  • Once per session. A note is served once, not for one-word turns, and not at all when nothing fits.

The cache keeps itself: each session is distilled once when it ends, newly merged pull requests are mined as they land, and a maintenance run every four hours re-verifies stale notes and archives the ones sessions never acted on. See Keeping it current.

Why does mining take so long? Can I skip it?

Each merged pull request is read by a frontier model through your agent's login: title, description, review comments and the diff, about 14k tokens and 8 seconds per pull request, four at a time. The default build reads up to 60 of them, then reads the design documents and writes search phrasings for every new note, each a model call. Rate limits on the login stretch it further. The estimate in tokens and minutes is shown before anything is spent.

Yes, you can skip it, and nothing stops working:

  • Press Skip for now on the warm-up view, or run thinker setup --no-build. Thinker is wired and the cache grows from your own sessions.
  • Pick Shallow: the newest 30% of the same pull requests.
  • Stopping a build at any point keeps every note saved so far. thinker mine-prs continues where it stopped, 20 pull requests at a time, and the background maintenance mines a few new ones per run anyway.

What a build gives you that sessions cannot is the record of past fixes. A repository with little history loses little by skipping it.

How can I tell if Thinker is helping my agents?

  • At the end of each turn one line says what was served and the code it pointed at. It does not say "saved": whether the agent acted on a note is known only once the session is assessed.
  • The Context page, and thinker context, show where your agents' context goes: what each instruction section, skill and tool costs a session and how often sessions acted on it, so what you cut is measured on your own sessions.
  • thinker usage, and the usage under Cache in thinker ui, show notes served, what the sessions did with them (confirmed, contradicted, unused), what learning and maintenance cost in tokens, and an estimate of the reads avoided.
  • The holdout is measured, not estimated. 15% of prompts are served nothing, chosen by a hash of the session and the turn, and what every turn cost is read from the session's transcript. Once twenty prompts stand on each side, the holdout section compares the cost per prompt: tool calls and tokens with notes against without, on your repository, by your agent.

A note served is not a note used. Read the confirmed and unused counts rather than the hit rate; a cache that serves often and is rarely acted on is costing tokens, and maintenance archives such notes over time.
