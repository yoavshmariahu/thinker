When a shared metric is attached to an experiment, it can end up with the same internal identifier as one of the experiment's own inline metrics. Because experiment results are matched to metrics by that identifier, one metric then displays the other's results, which is wrong and confusing. An earlier fix prevented this between two inline metrics, but two scenarios still produce the clash. First, when a user promotes an inline metric to a shared metric, the new shared metric keeps the original's identifier, and if the inline copy remains on the experiment, the two collide. The guidance given to agents for setting up experiment analytics also tells them to promote a metric with the same query and then attach it, which leads straight to this situation. Second, when an experiment is updated with only a new list of attached shared metrics, the experiment's existing inline metrics are never checked against them, so a clash can slip through. Desired behavior: inline and shared metrics on the same experiment should always have distinct identifiers, whether the shared metric is created by promotion or attached through an update that changes only the attached shared metrics. Each metric should always show its own results, and the agent guidance should stop recommending the flow that causes the duplication.
