# Desired behaviors of skills

Rules the code must uphold, kept as `behavior` notes in `.thinker/notes/` and checked by `thinker review` and `thinker verify`. A **fixed** behavior is never revised; a **mutable** one is revised only by a change that edits its note. Generated by `thinker system md`; edit the notes, not this file.

## Fixed

### A review never writes to the cache

*fixed; id `a-review-never-writes-to-the-cache`; **unverified***

`thinker review` and the MCP `review` tool read the notes and the change without modifying knowledge notes: no note is created, rewritten, re-hashed, retired or marked stale by a review, whatever the verdict. Review may write usage and impact records, and task verification may persist local task context, frozen inputs, execution evidence and human reports under `.thinker/local/reviews/`, with local Git snapshot refs. These are evidence artifacts, not shared or local knowledge notes; they never rewrite the notes used to assess a candidate. A note the review finds outdated or already stale is reported with the `thinker verify` command that re-checks it; the change under review may never be merged, so it must not move the cache.
The per-note assessment (src/review.js:assessNote) and the behavior assessment (src/review.js:assessBehavior) return their verdicts and corrections as data only; the holistic call (src/review.js:assessHolistic) likewise.

Upheld at: `src/review.js:review`, `src/review.js:assessNote`, `src/review.js:assessBehavior`, `src/review.js:assessHolistic`, `src/store.js:log`

### Serving and assessment never rewrite a shared note's committed file

*fixed; id `serving-and-assessment-never-rewrite-a-shared-note-s-committ`; **unverified***

Files under `.thinker/notes/` change only through an explicit `thinker share` (src/store.js:Store.promote), a sync pull, or a person editing them. Everything a checkout learns about a shared note (uses, servedIn, attest, status, staleness, a pending correction) goes to the overlay under `.thinker/local/shared/`: src/store.js:Store.put writes the overlay and leaves the committed file as it is whenever `isShared(id)`. So orienting, lookups, the end-of-session assessment (src/ops.js:attest) and background verification can run on every checkout without producing a dirty working tree or a merge conflict in the notes.

Upheld at: `src/store.js:Store.put`, `src/store.js:Store.promote`, `src/ops.js:attest`

### Verification never retires a desired behavior, and rewrites one only to match merged code

*fixed; id `verification-never-rewrites-or-retires-a-desired-behavior`; **unverified***

A `behavior` note is a rule a person wrote. When its deps change, src/ops.js:verifyNote hands it to src/ops.js:verifyBehavior, whose verdicts are `holds` (re-baseline), `moved` (deps re-pointed, history kept), and for code that no longer upholds it either `broken` or `revised`, decided by src/ops.js:onDefaultBranch: code that is not merged (a working tree, a branch, unpushed commits) leaves the text alone and sets status `violated` with the commit and reason; code merged on the default branch is the truth, and the behavior's body is replaced with what the code upholds now, the old body kept in `history` and `revised` recording the commit and reason. No path sets a behavior to `invalid`, lowers its confidence, or rewrites it for unmerged code; the ordinary verdicts `update` and `invalid` never reach a behavior.

Upheld at: `src/ops.js:verifyNote`, `src/ops.js:verifyBehavior`, `src/ops.js:onDefaultBranch`

### THINKER_TELEMETRY=off and test runs send no telemetry

*fixed; id `thinker-telemetry-off-and-test-runs-send-no-telemetry`*

src/telemetry.js:isTelemetryEnabled returns false before any other check when `THINKER_TELEMETRY` is `off`, `0` or `false`, when `THINKER_NO_TELEMETRY=1`, or when `THINKER_NO_LEARN=1`; a test run (`THINKER_TEST=1`, or Node's own test context) never reaches the production endpoint. Every send goes through this gate, so tests, benchmarks, evaluation harnesses and CI reviews that set the variable are not counted as installs or usage. The order matters: the environment switch must win over any repository config or scheduled job that would turn telemetry on.

Upheld at: `src/telemetry.js:isTelemetryEnabled`

## Mutable

### The prompt hooks serve no stale note

*mutable; id `the-prompt-hooks-serve-no-stale-note`; **unverified***

At prompt time a note whose deps no longer match the working tree is held back, not served: src/ops.js:orient with `freshOnly` takes stale notes out of the servable set and logs them as `held`. Reading or withholding a note never launches verification. src/maintain.js:maintain runs a batch at most once every four hours on the next repository activity, using changed dependencies and diffs since each note was verified, subject to recent-use, churn and token limits. Once fresh again the note can be served on a later turn. Meanwhile the agent can explicitly request stale notes through `orient` or `lookup`, with the STALE banner. Manual `thinker verify` remains immediate.

Upheld at: `src/ops.js:orient`, `src/maintain.js:maintain`

### A note under review must never be handed over as fact until it passes re-checking.

*mutable; id `a-note-under-review-must-never-be-handed-over-as-fact-until`*

When the code under a note changes, the note is re-checked in the background, and it must not be served as established fact until that check passes. This guards against agents acting on knowledge that may no longer match the code, enforced through the serving path in src/cache-guidance.js:agentWorkflow and the notes command in src/commands/notes.js:systemCommand.

Upheld at: `src/cache-guidance.js:agentWorkflow`, `src/commands/notes.js:systemCommand`

### A skill the code contradicts must not be handed over until fixed or reviewed.

*mutable; id `a-skill-the-code-contradicts-must-not-be-handed-over-until-f`*

Each skill file is audited against the code it talks about, and when the audit finds the code contradicts the skill, that skill is listed with its issues and withheld from being served as valid until it is fixed or explicitly reviewed. Among skills that do the same thing, only the one session evidence confirms is actually served. This is enforced in the serving/guidance path such as src/cache-guidance.js:agentWorkflow.

Upheld at: `src/cache-guidance.js:agentWorkflow`

### All model calls route through the user's own already-authenticated coding agent login, never a separate credential.

*mutable; id `all-model-calls-route-through-the-user-s-own-already-authent`*

Model calls must go through the coding agent the user already uses, under its own login, rather than thinker managing or sending its own API keys. This is enforced during setup and client wiring, e.g. src/setup/agents.js:selectAndAuthenticateAgent and src/clients.js:installClient / refreshWiring, and at call time via src/llm.js:viaOther.

Upheld at: `src/setup/agents.js:selectAndAuthenticateAgent`, `src/clients.js:installClient`, `src/llm.js:viaOther`

### All thinker state stays inside the repository's .thinker/ folder.

*mutable; id `all-thinker-state-stays-inside-the-repository-s-thinker-fold`*

Everything thinker produces and stores must remain within the repository's .thinker/ folder rather than in external services or global locations, keeping the cache local to the repo. This is upheld by the setup and build steps that create and populate that folder, such as src/setup.js:runSetup and src/setup/steps.js:stepBuildCache.

Upheld at: `src/setup.js:runSetup`, `src/setup/steps.js:stepBuildCache`

### Download credentials are a separate, long-lived HMAC credential scoped only to installer/archive/version files and must never authorize docs access or mint a browser session.

*mutable; id `download-credentials-are-a-separate-long-lived-hmac-credenti`*

A successful login returns a private installation command whose download token is a distinct HMAC credential from the session cookie, limited to installer, archive, and version files, and incapable of authorizing docs or creating a session. These tokens intentionally last until key rotation rather than expiring after seven days, so unattended updates keep working; they must be treated like passwords. This separation is enforced in gateway.js's hash/sign/matched logic distinguishing session vs download scopes.

Upheld at: `infra/access/gateway.js:sign`, `infra/access/gateway.js:hash`, `infra/access/gateway.js:matched`

### Each report's file_key must be unique so duplicate imports or retried invocations never create duplicate rows.

*mutable; id `each-report-s-file-key-must-be-unique-so-duplicate-imports-o`*

Historical reports keep their S3 object key and new reports use the API Gateway request ID as file_key, and this uniqueness constraint prevents re-ingestion or repeated Lambda invocations for the same request from duplicating data. This is upheld by infra/metrics/report.mjs (insertReport, existing, columns) and scripts/metrics-db.js (insertReport, ingested, skipped) which detect and skip already-present keys.

Upheld at: `infra/metrics/report.mjs:insertReport`, `infra/metrics/report.mjs:existing`, `infra/metrics/report.mjs:columns`, `scripts/metrics-db.js:insertReport`, `scripts/metrics-db.js:ingested`, `scripts/metrics-db.js:skipped`

### Historical reports and unavailable device IDs must remain NULL rather than be guessed or backfilled.

*mutable; id `historical-reports-and-unavailable-device-ids-must-remain-nu`*

Because device IDs cannot reliably be inferred from installation IDs alone, old reports and clients without a device ID keep device_id as NULL instead of a fabricated or inferred value. This is upheld by infra/metrics/report.mjs (normalizeReport, value) which leaves the field null rather than synthesizing it.

Upheld at: `infra/metrics/report.mjs:normalizeReport`, `infra/metrics/report.mjs:value`

### Session cookies must be signed, scoped to seven days, set with Secure/HttpOnly/SameSite=Strict, and the browser must never store the raw access code or see credentials in public HTML.

*mutable; id `session-cookies-must-be-signed-scoped-to-seven-days-set-with`*

GET /access/session accepts the code via X-Thinker-Access-Code, hashes it with SHA-256 for comparison against the secret, and on success sets a signed __Host-thinker_session cookie valid seven days with Secure; HttpOnly; SameSite=Strict. The browser must never store the access code, and public HTML must contain no credentials. This is implemented via gateway.js's hash/sign/sessionValid/cookie/expires logic and SESSION_SECONDS/COOKIE constants.

Upheld at: `infra/access/gateway.js:sign`, `infra/access/gateway.js:hash`, `infra/access/gateway.js:sessionValid`, `infra/access/gateway.js:cookie`, `infra/access/gateway.js:SESSION_SECONDS`, `infra/access/gateway.js:COOKIE`

### The PostgreSQL writer must commit a report to the database before acknowledging receipt.

*mutable; id `the-postgresql-writer-must-commit-a-report-to-the-database-b`*

The writer only replies success once PostgreSQL has durably stored the report, so clients never receive a false acknowledgment for data that was not saved. This is enforced in infra/metrics/handler.js (createHandler, reply) which only replies after the insert in infra/metrics/report.mjs (insertReport) completes, and relies on the normalized row/result from normalizeReport.

Upheld at: `infra/metrics/handler.mjs:createHandler`, `infra/metrics/handler.mjs:reply`, `infra/metrics/report.mjs:insertReport`, `infra/metrics/report.mjs:normalizeReport`

### The raw device/machine identifier must never leave the device; only its hashed form is ever sent or stored.

*mutable; id `the-raw-device-machine-identifier-must-never-leave-the-devic`*

Clients compute deviceId as a Thinker-specific HMAC-SHA256 hash of the OS machine identifier and only transmit that hash, keeping the underlying OS identifier private. The nullable reports.device_id column, populated via infra/metrics/messages.mjs (normalizeMessage) and infra/metrics/report.mjs (normalizeReport), stores only this hashed value, never the raw ID.

Upheld at: `infra/metrics/messages.mjs:normalizeMessage`, `infra/metrics/report.mjs:normalizeReport`

### Thinker keeps each learned note pointed at the exact code it describes.

*mutable; id `thinker-keeps-each-learned-note-pointed-at-the-exact-code-it`*

Notes written from merged pull requests and agent sessions must point at the exact code they describe, so they stay tied to the code they describe rather than drifting into generic advice. This is upheld by the note-serving and cache-building pipeline, e.g. src/setup/steps.js:stepBuildCache and src/cache-guidance.js:agentWorkflow which govern how notes are built and surfaced tied to code locations.

Upheld at: `src/setup/steps.js:stepBuildCache`, `src/cache-guidance.js:agentWorkflow`

### WAF must rate-limit /access/session to about 30 requests per source IP per five-minute window, returning 429, and access/session logging must stay disabled to avoid logging credentials.

*mutable; id `waf-must-rate-limit-access-session-to-about-30-requests-per`*

The gateway deployment configures WAF to cap /access/session (including session-restoration requests) at roughly 30 requests per IP per five minutes, responding 429 beyond that, understanding AWS limits are approximate and shared IPs share the budget. WAF sampling and CloudFront access logging must remain disabled so credentials are never written to logs. This is set up in infra/access/deploy.mjs's policy/block configuration during prepare/apply.

Upheld at: `infra/access/deploy.mjs:policy`, `infra/access/deploy.mjs:block`
