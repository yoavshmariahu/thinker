# Desired behaviors of warm-up-onboarding

Rules the code must uphold, kept as `behavior` notes in `.thinker/notes/` and checked by `thinker review` and `thinker verify`. A **fixed** behavior is never revised; a **mutable** one is revised only by a change that edits its note. Generated by `thinker system md`; edit the notes, not this file.

## Fixed

### A review never writes to the cache

*fixed; id `a-review-never-writes-to-the-cache`; **unverified***

`thinker review` and the MCP `review` tool read the notes and the change without modifying knowledge notes: no note is created, rewritten, re-hashed, retired or marked stale by a review, whatever the verdict. Review may write usage and impact records, and task verification may persist local task context, frozen inputs, execution evidence and human reports under `.thinker/local/reviews/`, with local Git snapshot refs. These are evidence artifacts, not shared or local knowledge notes; they never rewrite the notes used to assess a candidate. A note the review finds outdated or already stale is reported with the `thinker verify` command that re-checks it; the change under review may never be merged, so it must not move the cache.
The per-note assessment (src/review.js:assessNote) and the behavior assessment (src/review.js:assessBehavior) return their verdicts and corrections as data only; the holistic call (src/review.js:assessHolistic) likewise.

Upheld at: `src/review.js:review`, `src/review.js:assessNote`, `src/review.js:assessBehavior`, `src/review.js:assessHolistic`, `src/store.js:log`

### Serving and assessment never rewrite a shared note's committed file

*fixed; id `serving-and-assessment-never-rewrite-a-shared-note-s-committ`; **unverified***

Files under `.thinker/notes/` change only through an explicit `thinker share` (src/store.js:Store.promote), a sync pull, or a person editing them. Everything a checkout learns about a shared note (uses, servedIn, attest, status, staleness, a pending correction) goes to the overlay under `.thinker/local/shared/`: src/store.js:Store.put writes the overlay and leaves the committed file as it is whenever `isShared(id)`. So orienting, lookups, the end-of-session assessment (src/ops.js:attest) and background verification can run on every checkout without producing a dirty working tree or a merge conflict in the notes.

Upheld at: `src/store.js:Store.put`, `src/store.js:Store.promote`, `src/ops.js:attest`

### Verification never retires a desired behavior, and rewrites one only to match merged code

*fixed; id `verification-never-rewrites-or-retires-a-desired-behavior`; **unverified***

A `behavior` note is a rule a person wrote. When its deps change, src/ops.js:verifyNote hands it to src/ops.js:verifyBehavior, whose verdicts are `holds` (re-baseline), `moved` (deps re-pointed, history kept), and for code that no longer upholds it either `broken` or `revised`, decided by src/ops.js:onDefaultBranch: code that is not merged (a working tree, a branch, unpushed commits) leaves the text alone and sets status `violated` with the commit and reason; code merged on the default branch is the truth, and the behavior's body is replaced with what the code upholds now, the old body kept in `history` and `revised` recording the commit and reason. No path sets a behavior to `invalid`, lowers its confidence, or rewrites it for unmerged code; the ordinary verdicts `update` and `invalid` never reach a behavior.

Upheld at: `src/ops.js:verifyNote`, `src/ops.js:verifyBehavior`, `src/ops.js:onDefaultBranch`

### THINKER_TELEMETRY=off and test runs send no telemetry

*fixed; id `thinker-telemetry-off-and-test-runs-send-no-telemetry`*

src/telemetry.js:isTelemetryEnabled returns false before any other check when `THINKER_TELEMETRY` is `off`, `0` or `false`, when `THINKER_NO_TELEMETRY=1`, or when `THINKER_NO_LEARN=1`; a test run (`THINKER_TEST=1`, or Node's own test context) never reaches the production endpoint. Every send goes through this gate, so tests, benchmarks, evaluation harnesses and CI reviews that set the variable are not counted as installs or usage. The order matters: the environment switch must win over any repository config or scheduled job that would turn telemetry on.

Upheld at: `src/telemetry.js:isTelemetryEnabled`

## Mutable

### The prompt hooks serve no stale note

*mutable; id `the-prompt-hooks-serve-no-stale-note`; **unverified***

At prompt time a note whose deps no longer match the working tree is held back, not served: src/ops.js:orient with `freshOnly` takes stale notes out of the servable set and logs them as `held`. Reading or withholding a note never launches verification. src/maintain.js:maintain runs a batch at most once every four hours on the next repository activity, using changed dependencies and diffs since each note was verified, subject to recent-use, churn and token limits. Once fresh again the note can be served on a later turn. Meanwhile the agent can explicitly request stale notes through `orient` or `lookup`, with the STALE banner. Manual `thinker verify` remains immediate.

Upheld at: `src/ops.js:orient`, `src/maintain.js:maintain`

### A note under re-check must never be handed to an agent as fact until it passes again.

*mutable; id `a-note-under-re-check-must-never-be-handed-to-an-agent-as-fa`*

When the code underlying a note changes, thinker re-verifies the note in the background, and the note must not be served as established knowledge during that time. This keeps agents from acting on claims that may no longer hold after the code moved. Verification output and status gating is produced by src/verification.js:renderVerification.

Upheld at: `src/verification.js:renderVerification`

### Behaviors enforced by review must come only from design documents checked into the repository.

*mutable; id `behaviors-enforced-by-review-must-come-only-from-design-docu`*

The rules thinker checks changes against are sourced from READMEs and design documents committed alongside the code, not from external or inferred sources, and users can add, change, or remove them by asking their agent. This keeps the source of truth auditable and under the team's control. src/commands/doctor.js:runChecks and src/cli.js:main surface these behaviors via the system docs path.

Upheld at: `src/commands/doctor.js:runChecks`, `src/cli.js:main`

### Database bootstrap preserves existing role passwords when rerun.

*mutable; id `database-bootstrap-preserves-existing-role-passwords-when-re`*

Rerunning the metrics database bootstrap script must not regenerate or overwrite existing database credentials. In infra/metrics/bootstrap.mjs:users, user account provisioning verifies whether roles already exist rather than resetting their passwords. The process coordinates with infra/metrics/bootstrap.mjs:secrets so running clients continue operating uninterrupted.

Upheld at: `infra/metrics/bootstrap.mjs:users`, `infra/metrics/bootstrap.mjs:secrets`

### Deployment parameters passed to the AWS CLI are written to a private temporary file with mode 0600 and deleted after the command.

*mutable; id `deployment-parameters-passed-to-the-aws-cli-are-written-to-a`*

To protect sensitive credentials during infrastructure deployment, arguments are not passed directly on the command line. In infra/metrics/deploy.mjs:parameters, input parameters are written to a temporary file infra/metrics/deploy.mjs:input inside infra/metrics/deploy.mjs:scratch with restricted permissions of mode 0600. Once the command completes, this temporary file is deleted to avoid leaving credentials on disk.

Upheld at: `infra/metrics/deploy.mjs:parameters`, `infra/metrics/deploy.mjs:scratch`, `infra/metrics/deploy.mjs:input`

### Model calls must go through the user's own already-authenticated coding agent login, never a separate credential.

*mutable; id `model-calls-must-go-through-the-user-s-own-already-authentic`*

Thinker does not introduce its own API keys or accounts for model access; it reuses the coding agent the user already has logged in. This avoids extra credential handling and keeps usage tied to the agent's existing billing and auth. Agent selection and authentication reuse is handled by src/setup/agents.js:selectAndAuthenticateAgent and dispatched through src/llm.js:viaOther.

Upheld at: `src/setup/agents.js:selectAndAuthenticateAgent`, `src/llm.js:viaOther`

### Notes thinker writes must each point at the exact code they describe.

*mutable; id `notes-thinker-writes-must-each-point-at-the-exact-code-they`*

Notes are generated from merged pull requests and agent sessions, and must be tied to the specific code they describe rather than floating free text. This linkage is what lets later steps check whether a note is still accurate and serve it only for relevant code. The note-writing and code-pointer logic lives in src/distill.js:DISTILL_SYSTEM.

Upheld at: `src/distill.js:DISTILL_SYSTEM`

### Repeated imports and Lambda invocations for the same API request cannot duplicate a report.

*mutable; id `repeated-imports-and-lambda-invocations-for-the-same-api-req`*

Telemetry ingestion deduplicates reports by relying on unique request keys. In infra/metrics/handler.mjs:createHandler, the API Gateway request identifier is extracted as infra/metrics/handler.mjs:key. When persisting via infra/metrics/report.mjs:insertReport, existing entries identified by infra/metrics/report.mjs:existing prevent duplicate records from being inserted on repeated invocations.

Upheld at: `infra/metrics/handler.mjs:createHandler`, `infra/metrics/handler.mjs:key`, `infra/metrics/report.mjs:insertReport`, `infra/metrics/report.mjs:existing`

### Rotating the access code alone must not revoke existing sessions or download credentials; only replacing signingKey does.

*mutable; id `rotating-the-access-code-alone-must-not-revoke-existing-sess`*

To revoke existing sessions and download credentials, signingKey must be replaced with a fresh cryptographically random 32-byte key encoded as 64 hex characters, in addition to any code change. Code-only rotation leaves previously issued sessions and download URLs valid. This is enforced by infra/access/gateway.js (sign, hash, hashes, matched) which derive validity from signingKey rather than accessCode alone.

Upheld at: `infra/access/gateway.js:sign`, `infra/access/gateway.js:hashes`, `infra/access/gateway.js:matched`

### Session and download credentials must be distinct, with the download token unable to authorize docs access or mint a browser session.

*mutable; id `session-and-download-credentials-must-be-distinct-with-the-d`*

A successful login returns a private installation command containing a separate HMAC download token scoped only to installer/archive/version files; it cannot be used to gain docs access or create a session cookie. The session cookie itself is a signed, seven-day __Host-thinker_session cookie with Secure, HttpOnly, SameSite=Strict attributes. Both credential types are produced and validated in infra/access/gateway.js (sign, hash, sessionValid, codeValid, cookie).

Upheld at: `infra/access/gateway.js:sign`, `infra/access/gateway.js:sessionValid`, `infra/access/gateway.js:cookie`

### The live integration smoke check removes its own synthetic reports using the administrative login, including on failure.

*mutable; id `the-live-integration-smoke-check-removes-its-own-synthetic-r`*

Synthetic reports generated during integration testing must not linger in the metrics database. In infra/metrics/smoke.mjs:invoke, test runs inject synthetic telemetry identified by keys tracked in infra/metrics/smoke.mjs:keys. The smoke test uses an administrative database connection in infra/metrics/smoke.mjs:admin to purge these synthetic records even if an error occurs during execution.

Upheld at: `infra/metrics/smoke.mjs:admin`, `infra/metrics/smoke.mjs:keys`, `infra/metrics/smoke.mjs:invoke`

### The system must never log or expose access codes or session/download credentials, and must prevent bypassing the gateway via direct S3 access.

*mutable; id `the-system-must-never-log-or-expose-access-codes-or-session`*

The browser stores no access code, the public HTML contains no credentials, WAF sampling and CloudFront access logging are disabled to avoid logging credentials, and protected responses use Cache-Control: private, no-store. S3 blocks public access and permits reads only from the CloudFront distribution, so the gateway cannot be bypassed via a direct object URL. This is enforced by response construction in infra/access/gateway.js (response, equal, difference) and the S3 bucket policy set up in infra/access/deploy.mjs (policy, block).

Upheld at: `infra/access/gateway.js:response`, `infra/access/deploy.mjs:policy`, `infra/access/deploy.mjs:block`

### The telemetry ingestion service acknowledges a report only after PostgreSQL commits it.

*mutable; id `the-telemetry-ingestion-service-acknowledges-a-report-only-a`*

Incoming telemetry reports received over HTTP are processed by infra/metrics/handler.mjs:createHandler. The handler delegates persistence to infra/metrics/report.mjs:insertReport to insert the record into PostgreSQL. Only after the database transaction successfully commits does infra/metrics/handler.mjs:reply return an acknowledgment response to the caller.

Upheld at: `infra/metrics/handler.mjs:createHandler`, `infra/metrics/handler.mjs:reply`, `infra/metrics/report.mjs:insertReport`

### thinker review must flag a change that reintroduces a fixed bug or violates a written-down team rule.

*mutable; id `thinker-review-must-flag-a-change-that-reintroduces-a-fixed`*

Review compares an incoming change against the behaviors derived from design documents and against previously fixed bugs, surfacing violations before merge. This is the core guarantee of the review command and is implemented in src/review.js:reviewImpl and rendered by src/review.js:renderReview, with output assembly in src/review-post.js:buildReview.

Upheld at: `src/review.js:reviewImpl`, `src/review.js:renderReview`, `src/review-post.js:buildReview`
