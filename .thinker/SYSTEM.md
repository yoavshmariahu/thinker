# Desired behaviors of thinker-npx

Rules the code must uphold, kept as `behavior` notes in `.thinker/notes/` and checked by `thinker review` and `thinker verify`. A **fixed** behavior is never revised; a **mutable** one is revised only by a change that edits its note. Generated by `thinker system md`; edit the notes, not this file.

## Fixed

### A review never writes to the cache

*fixed; id `a-review-never-writes-to-the-cache`; **unverified***

`thinker review` and the MCP `review` tool read the notes and the change without modifying knowledge notes: no note is created, rewritten, re-hashed, retired or marked stale by a review, whatever the verdict. Review may write usage and impact records, and task verification may persist local task context, frozen inputs, execution evidence and human reports under `.thinker/local/reviews/`, with local Git snapshot refs. These are evidence artifacts, not shared or local knowledge notes; they never rewrite the notes used to assess a candidate. A note the review finds outdated or already stale is reported with the `thinker verify` command that re-checks it; the change under review may never be merged, so it must not move the cache.
The per-note assessment (src/review.js:assessNote) and the behavior assessment (src/review.js:assessBehavior) return their verdicts and corrections as data only; the holistic call (src/review.js:assessHolistic) likewise.

Upheld at: `src/review.js:review`, `src/review.js:assessNote`, `src/review.js:assessBehavior`, `src/review.js:assessHolistic`, `src/store.js:log`

### Serving and assessment never rewrite a shared note's committed file

*fixed; id `serving-and-assessment-never-rewrite-a-shared-note-s-committ`; **unverified***

Files under `.thinker/notes/` change only through an explicit `thinker share` (src/store.js:Store.promote), a sync pull, or a person editing them. Everything a checkout learns about a shared note (uses, servedIn, attest, status, staleness, a pending correction) goes to the overlay under `.thinker/local/shared/`: src/store.js:Store.put writes the overlay and leaves the committed file as it is whenever `isShared(id)`. So orienting, lookups, the end-of-session assessment (src/ops.js:attest) and background verification can run on every checkout without producing a dirty working tree or a merge conflict in the notes.

Upheld at: `src/store.js:Store.put`, `src/store.js:Store.promote`, `src/ops.js:attest`

### Verification never retires a desired behavior, and rewrites one only to match merged code

*fixed; id `verification-never-rewrites-or-retires-a-desired-behavior`; **unverified***

A `behavior` note is a rule a person wrote. When its deps change, src/ops.js:verifyNote hands it to src/ops.js:verifyBehavior, whose verdicts are `holds` (re-baseline), `moved` (deps re-pointed, history kept), and for code that no longer upholds it either `broken` or `revised`, decided by src/ops.js:onDefaultBranch: code that is not merged (a working tree, a branch, unpushed commits) leaves the text alone and sets status `violated` with the commit and reason; code merged on the default branch is the truth, and the behavior's body is replaced with what the code upholds now, the old body kept in `history` and `revised` recording the commit and reason. No path sets a behavior to `invalid`, lowers its confidence, or rewrites it for unmerged code; the ordinary verdicts `update` and `invalid` never reach a behavior.

Upheld at: `src/ops.js:verifyNote`, `src/ops.js:verifyBehavior`, `src/ops.js:onDefaultBranch`

### THINKER_TELEMETRY=off and test runs send no telemetry

*fixed; id `thinker-telemetry-off-and-test-runs-send-no-telemetry`*

src/telemetry.js:isTelemetryEnabled returns false before any other check when `THINKER_TELEMETRY` is `off`, `0` or `false`, when `THINKER_NO_TELEMETRY=1`, or when `THINKER_NO_LEARN=1`; a test run (`THINKER_TEST=1`, or Node's own test context) never reaches the production endpoint. Every send goes through this gate, so tests, benchmarks, evaluation harnesses and CI reviews that set the variable are not counted as installs or usage. The order matters: the environment switch must win over any repository config or scheduled job that would turn telemetry on.

Upheld at: `src/telemetry.js:isTelemetryEnabled`

## Mutable

### The prompt hooks serve no stale note

*mutable; id `the-prompt-hooks-serve-no-stale-note`; **unverified***

At prompt time a note whose deps no longer match the working tree is held back, not served: src/ops.js:orient with `freshOnly` takes stale notes out of the servable set and logs them as `held`. Reading or withholding a note never launches verification. src/maintain.js:maintain runs a batch at most once every four hours on the next repository activity, using changed dependencies and diffs since each note was verified, subject to recent-use, churn and token limits. Once fresh again the note can be served on a later turn. Meanwhile the agent can explicitly request stale notes through `orient` or `lookup`, with the STALE banner. Manual `thinker verify` remains immediate.

Upheld at: `src/ops.js:orient`, `src/maintain.js:maintain`

### A note is never handed over as fact until it is rechecked and passes after the code it depends on changes

*mutable; id `a-note-is-never-handed-over-as-fact-until-it-is-rechecked-an`*

When the code under a note changes, thinker must re-check the note in the background, and the note must not be served as settled truth until it passes that check. This keeps agents from acting on stale guidance. This is enforced by the prompt/cache guidance logic in src/cache-guidance.js:agentWorkflow and the notes serving path in src/commands/notes.js:systemCommand.

Upheld at: `src/cache-guidance.js:agentWorkflow`, `src/commands/notes.js:systemCommand`

### A skill the code contradicts must be withheld until it is fixed or reviewed

*mutable; id `a-skill-the-code-contradicts-must-be-withheld-until-it-is-fi`*

Each checked-in SKILL.md is audited as a card and checked against the code it describes; if the audit finds a contradiction with the code, that skill must be listed with its issues and not handed over until fixed or reviewed. Among duplicate skills doing the same thing, only the one sessions confirm is served. This is upheld by src/commands/doctor.js:runChecks and src/commands/notes.js:systemCommand.

Upheld at: `src/commands/doctor.js:runChecks`, `src/commands/notes.js:systemCommand`

### Device IDs must never be inferred or backfilled for historical or unavailable reports

*mutable; id `device-ids-must-never-be-inferred-or-backfilled-for-historic`*

reports.device_id stays NULL for historical reports and for clients where the identifier is unavailable; the system must not guess or reconstruct device IDs from installation IDs. This is enforced by infra/metrics/report.mjs's normalizeReport, which only sets device_id when the client explicitly supplies it, leaving it NULL otherwise.

Upheld at: `infra/metrics/report.mjs:normalizeReport`

### Protected content must be withheld by the gateway itself, never merely hidden client-side, and must never be cached as shared/public.

*mutable; id `protected-content-must-be-withheld-by-the-gateway-itself-nev`*

Anonymous docs requests redirect to the landing page and return to the originally requested docs path/fragment after login; the document states content is withheld by the gateway, not hidden by JavaScript, and protected responses use Cache-Control: private, no-store. This is upheld by the response construction in infra/access/gateway.js:response and the redirect/sessionValid checks.

Upheld at: `infra/access/gateway.js:response`, `infra/access/gateway.js:sessionValid`

### Repeated imports or repeated Lambda invocations for the same request must never duplicate a report

*mutable; id `repeated-imports-or-repeated-lambda-invocations-for-the-same`*

file_key is unique per report: historical reports keep their S3 object key and new reports use the API Gateway request ID, so re-running the importer or re-invoking the Lambda for the same request cannot create duplicate rows. This is enforced via infra/metrics/report.mjs's normalizeReport/insertReport using the existing-row check, and scripts/metrics-db.js's insertReport/ingested/skipped bookkeeping for re-imports.

Upheld at: `infra/metrics/report.mjs:normalizeReport`, `infra/metrics/report.mjs:insertReport`, `infra/metrics/report.mjs:existing`, `scripts/metrics-db.js:insertReport`

### S3 must stay private, readable only via the CloudFront distribution, so the gateway cannot be bypassed through a direct object URL.

*mutable; id `s3-must-stay-private-readable-only-via-the-cloudfront-distri`*

The document requires the S3 origin to block public access and allow reads only from the specific CloudFront distribution, preventing bypass of the access gateway. This policy is applied/verified in deployment code via infra/access/deploy.mjs:policy and infra/access/deploy.mjs:block, and checked by the smoke test's bypass attempts.

Upheld at: `infra/access/deploy.mjs:policy`, `infra/access/deploy.mjs:block`, `infra/access/smoke.mjs:response`

### The browser never stores or transmits the raw access code; sessions use a signed, scoped HttpOnly cookie.

*mutable; id `the-browser-never-stores-or-transmits-the-raw-access-code-se`*

GET /access/session accepts the code only in the X-Thinker-Access-Code header, the gateway compares its SHA-256 hash to the stored configuration, and on success sets a signed seven-day __Host-thinker_session cookie with Secure; HttpOnly; SameSite=Strict. The public HTML must contain no credentials, and download tokens are a separate HMAC credential that cannot authorize docs or mint a session. This is enforced by infra/access/gateway.js's hash/hashes/matched/sign/cookie logic.

Upheld at: `infra/access/gateway.js:hash`, `infra/access/gateway.js:hashes`, `infra/access/gateway.js:matched`, `infra/access/gateway.js:sign`, `infra/access/gateway.js:cookie`

### The PostgreSQL writer must acknowledge a report only after PostgreSQL commits it

*mutable; id `the-postgresql-writer-must-acknowledge-a-report-only-after-p`*

Clients must receive success only once the report has actually been durably persisted, so acknowledgments cannot be sent on a write that later fails or rolls back. This is enforced in infra/metrics/handler.mjs's createHandler/reply flow and infra/metrics/report.mjs's insertReport, which commits before the handler replies.

Upheld at: `infra/metrics/handler.mjs:createHandler`, `infra/metrics/handler.mjs:reply`, `infra/metrics/report.mjs:insertReport`

### The raw per-device machine identifier must never leave the device

*mutable; id `the-raw-per-device-machine-identifier-must-never-leave-the-d`*

Only a Thinker-specific HMAC-SHA256 hash of the OS machine identifier (prefixed v1:) is sent and stored in the nullable reports.device_id column; the underlying OS identifier itself is never transmitted. This privacy boundary is enforced by infra/metrics/messages.mjs's normalizeMessage and infra/metrics/report.mjs's normalizeReport, which only accept/store the hashed deviceId field.

Upheld at: `infra/metrics/messages.mjs:normalizeMessage`, `infra/metrics/report.mjs:normalizeReport`

### The S3 importer must fail loudly rather than silently skip any report, and reject mismatched existing keys

*mutable; id `the-s3-importer-must-fail-loudly-rather-than-silently-skip-a`*

The importer validates single-part S3 ETags and payloads before writing, inserts and verifies every column and JSON payload within a transaction, and must error out the whole command on any problem instead of omitting a report. An existing file_key with different content must fail rather than being overwritten or ignored, per scripts/metrics-db.js's ingestJsonFiles/insertReport and infra/metrics/report.mjs's InvalidReport/existing checks.

Upheld at: `scripts/metrics-db.js:ingestJsonFiles`, `scripts/metrics-db.js:insertReport`, `infra/metrics/report.mjs:InvalidReport`, `infra/metrics/report.mjs:existing`

### Thinker learns notes from merged pull requests (fixes first) and agent sessions, each pointing at the exact code it describes

*mutable; id `thinker-learns-notes-from-merged-pull-requests-fixes-first-a`*

The system builds its cache by reading a repository's merged pull requests, prioritizing fixes, and its agent sessions, writing short notes describing what broke and why, what must not be undone, and how parts connect. Each note must point at the exact code it describes so it can be served and checked against that code. This is upheld by the cache build step and tooling in src/setup/steps.js:stepBuildCache and src/setup/steps.js:confirmCacheBuild.

Upheld at: `src/setup/steps.js:stepBuildCache`, `src/setup/steps.js:confirmCacheBuild`

### Uninstalling with --purge must remove a repository's hooks, MCP registration and notes, plus the machine-wide wiring

*mutable; id `uninstalling-with-purge-must-remove-a-repository-s-hooks-mcp`*

Running `thinker uninstall --user --purge` inside a repository must remove that repository's hooks, its MCP registration, and its notes, as well as the user's machine-wide wiring, leaving no residual integration behind. This is upheld by src/commands/setup.js:uninstallCommand.

Upheld at: `src/commands/setup.js:uninstallCommand`
